# 从形状推瓶颈

> Week 2 的五天各改一处. 改哪一处不是测出来的, 是从张量形状推出来的. 这篇给出那个推导要用的唯一一把尺子: 算术强度. 先从一个对不上的数字开始, 把 FMA、算术强度、矩阵单元的形状要求依次落地, 最后给出四个 Day 的瓶颈表和一张可以自己复算的表.

## 一个对不上的数字

Day 1 的 benchmark 里, Qwen3-0.6B 的 decode 是 34.20 tok/s, 即每个 token 29 ms. 权重是 596M 个参数, bf16 存放, 共 1.19 GB. 每次 decode 都要把全部权重读一遍.

M4 标称内存带宽 120 GB/s, 读完 1.19 GB 要 9.9 ms; 本机实测读写带宽约 80 GB/s, 要 14.9 ms. 实测每 token 29 ms, 是这两个下界的 2.9 倍与 1.95 倍.

这个差额不能全推给「实现没写好」. 它指向一个更基本的问题: 在这台机器上, 一个矩阵乘到底受什么限制? 答案取决于形状, 而形状在 prefill 和 decode 之间完全不同. 下面把这个依赖关系算清楚.

## 算力的单位是 FMA

GPU 标称的算力, 单位是每秒多少次浮点运算. 这个数不是从「一条加法指令」推出来的, 是从 FMA 推出来的.

FMA 是 fused multiply-add, 一条指令完成 `d = a * b + c`. 乘完直接进加法器, 中间结果不写回寄存器, 也不做舍入. 记作两次浮点运算.

所以一台机器的峰值算力是

```
峰值 FLOPs = 每周期能发的 FMA 数 × 频率 × 核心数 × 2
```

M4 的 10 核 GPU 标称 3.8 TFLOPS 的 bf16 算力, 本机实测峰值 3.2 TFLOPS (见下节表格最后一行), 对应每秒 1.6 万亿次 FMA.

这个数字与形状无关: 不管你算的是 4096×4096 的矩阵乘, 还是 4096 维的矩阵向量乘, FMA 单元的吞吐是固定的. 形状改变的不是「能算多快」, 是「这些 FMA 有多少时间在等数据」.

## 时间由两个下界里大的那个决定

一次矩阵乘要做两件事: 把数据搬进计算单元, 让 FMA 算. 两者可以重叠, 但不能互相替代. 所以耗时是

```
时间 = max(内存时间, 算力时间)
      = max(字节数 / 带宽, FLOP 数 / 峰值算力)
```

两边相除, 得到一个与机器无关的比值: 峰值算力除以带宽.

```
M4 标称: 3.8e12 FLOP/s ÷ 120e9 B/s = 32 FLOP/字节
M4 实测: 3.2e12 FLOP/s ÷ 80e9  B/s = 40 FLOP/字节
```

这个数的含义是: 每从内存搬来一个字节, 机器有能力做 32 到 40 次浮点运算. 如果一次计算里每个字节只被用了不到这个数, FMA 就会闲着, 时间由内存决定; 超过它, 内存就跟不上, 时间由算力决定. 下文用实测的 40 做判据, 因为实测的分子分母都是这台机器上量出来的.

这个比值叫算术强度 (arithmetic intensity), 记作 AI:

```
AI = FLOP 数 / 读入的字节数
```

## 同一个权重, 改变激活的行数

矩阵乘 `(M, E) @ (E, N)` 的算术强度随 M 线性增长. 每个输出元素要 E 次 FMA, 输出的元素数是 M·N, 所以 FLOP 数是 `2·M·N·E`; 读进来的是 `M·E + E·N` 个数, 当 M 远小于 N 时, 主导项是权重那 `E·N` 个.

```
AI ≈ 2·M·N·E / (2·E·N) = M
```

也就是说, 激活的行数就是算术强度. decode 时 M = 1, AI = 1; prefill 时 M = L, AI = L.

下面的脚本固定一个 4096×4096 的 bf16 权重 (32 MiB, 1677 万个元素), 把激活的行数从 1 加到 512, 量每次矩阵乘的耗时:

```python
import time

import mlx.core as mx

E = 4096
W = mx.random.normal((E, E)).astype(mx.bfloat16)
mx.eval(W)
print(f"权重 {W.nbytes / 2**20:.0f} MiB, 元素 {E * E:,}")


def bench(fn, warmup=5, iters=20):
    for _ in range(warmup):
        mx.eval(fn())
    ts = []
    for _ in range(iters):
        t0 = time.perf_counter()
        mx.eval(fn())
        ts.append(time.perf_counter() - t0)
    ts.sort()
    return ts[len(ts) // 2]


def time_matmul(M):
    x = mx.random.normal((M, E)).astype(mx.bfloat16)
    mx.eval(x)
    return bench(lambda: x @ W)


a = mx.random.normal((64 * 1024 * 1024,)).astype(mx.float32)
mx.eval(a)
bandwidth = 2 * a.nbytes / bench(lambda: a + 1.0)
peak = 2 * 512 * E * E / time_matmul(512)

print(f"权重 {W.nbytes / 2**20:.1f} MiB   "
      f"带宽 {bandwidth / 1e9:.1f} GB/s   "
      f"峰值 {peak / 1e12:.2f} TFLOPS   "
      f"比值 {peak / bandwidth:.1f} FLOP/字节")
print()
print(f"{'M':>4} {'搬运下界':>9} {'计算下界':>9} {'实测':>8}  谁主导")
mem = W.nbytes / bandwidth * 1e3
for M in (1, 2, 4, 8, 16, 32, 64, 128, 256, 512):
    compute = 2 * M * E * E / peak * 1e3
    print(f"{M:>4} {mem:>9.3f} {compute:>9.3f} {time_matmul(M) * 1e3:>8.3f}  "
          f"{'搬运' if compute < mem else '计算'}")
```

```text

   M      搬运下界      计算下界       实测  谁主导
   1     0.421     0.010    0.751  搬运
   2     0.421     0.021    0.682  搬运
   4     0.421     0.042    0.666  搬运
   8     0.421     0.083    0.678  搬运
  16     0.421     0.167    0.649  搬运
  32     0.421     0.333    0.773  搬运
  64     0.421     0.667    0.937  计算
 128     0.421     1.333    1.490  计算
 256     0.421     2.666    2.721  计算
 512     0.421     5.333    5.333  计算
```

中间两列一平一涨, 交点就是瓶颈切换的位置:

```text
耗时 ms
   5 ┤                                       ╱  计算 0.0104 × M
     │                                   ╱
   2 ┤                               ╱
     │                           ╱
   1 ┤                       ╱
     │                   ╱
 0.4 ┼───────────────╳─────────────────────  搬运 0.421, 与 M 无关
     │           ╱   M ≈ 40
     └──┬─────┬───┬────┬─────┬─────┬────
        1     8  32   64   128   256   512
```

**搬运下界是常数.** 33.5 MB 权重按 79.8 GB/s 搬一遍要 0.421 ms, 不管 M 是 1 还是 512 都是这个数.

**计算下界随 M 线性涨.** `2·M·4096²` 次浮点运算按 3.22 TFLOPS 除, M=1 要 0.010 ms, M=512 要 5.333 ms, 涨了 512 倍.

**实测贴着较大的那个下界走.** M=1 到 M=32 停在 0.65 到 0.77 之间, 因为这段时间计算最多只要 0.333 ms, 被 0.421 ms 的搬运盖住. M=64 之后开始跟着计算下界线性涨, M=512 时 5.333 与下界完全重合. M 很小时实测比下界高 0.2 到 0.3 ms, 那是启动和调度的固定开销, 不随 M 变.

**两条线在 M ≈ 40 相交**, 这个数就是 `峰值 ÷ 带宽 = 40.4`. 低于它, 多算几行几乎不花时间; 高于它, 每多一行都要多花 0.0104 ms.

同一份权重, M=512 时每个字节被用了 512 次, M=1 时只用 1 次. 耗时差 7.1 倍 (0.751 到 5.333), 运算量差 512 倍. 差额全部来自搬运被摊薄.

## 「退化」的准确含义

说「decode 的矩阵乘退化成矩阵向量乘」, 说的不是指令变了. 用的是同一批 FMA, 同一批矩阵块指令. 变的是形状, 形状决定了复用率, 复用率决定了上面那个 `max` 里哪一项占主导.

```
decode:  (1, E)   @ (E, N)   AI = 1      max(读权重, 10 µs)   = 读权重
prefill: (L, E)   @ (E, N)   AI = L      max(读权重, L×10 µs) = 算力 (L 大时)
```

同一个权重, 同一个算子, 因为激活的行数不同, 瓶颈从内存换到了算力. 这就是为什么 Day 2 和 Day 3 优化的是两件看起来矛盾的事: Day 2 把权重压小 (减少读取), Day 3 把权重留在片上复用 (增加复用). 它们各自对应 `max` 里的一项.

## 矩阵单元对 N 有形状要求

GPU 上有一类专门做矩阵乘的单元, 用一条指令算一小块矩阵, 而不是一个标量. NVIDIA 的叫 Tensor Core, Apple 的叫 simdgroup matrix.

这类指令有固定的块大小. NVIDIA 的 `mma.sync` 基本块是 m16n8k16, 意思是一次处理 16 行、8 列、深度 16. Apple 的 `simdgroup_matrix` 基本块是 8×8.

块大小是硬约束: 一次必须喂满这么多元素. 当 N = 1 时, 8 条列通道只有 1 条有数据, 利用率 1/8; 16 条行通道里也有大量空转. 所以 GEMV 一般不走矩阵单元, 退回普通 FMA, 让一个 threadgroup 沿 K 维归约一行.

这也解释了为什么不能简单地「把所有矩阵乘都交给矩阵单元」. 交给它之前要先问: 形状够不够填满它的块. 填不满, 它比普通 FMA 还慢.

## 为什么 cuBLAS 有两个函数

`cublasSgemv` 和 `cublasSgemm` 是两个不同的入口, 两套 kernel. 不是因为指令不同, 是因为调度策略不同.

GEMV 的任务是「读一个大矩阵, 每行和一个向量点积, 产出一个标量」. 它要的是把一个向量的读取摊给多个 warp, 每个 warp 算一部分, 最后树形归约. 权重只读一次, 没有复用, 优化的目标是让读取占满带宽.

GEMM 的任务是「读一个矩阵, 和另一个矩阵相乘」. 它要的是分块进共享内存或寄存器, 每块权重被多个输出行复用, 优化的目标是让 FMA 不闲着. 同一个 kernel 拿去跑 GEMV, 90% 的线程在算没用的输出.

用一句判据概括: 算术强度低于硬件比值时, 优化读取; 高于时, 优化复用. 两个方向用的 kernel 不一样.

## 同一道题的几种写法

Day 2 的 kernel 算出来的数，Task 1 的 Python 解包已经算过一遍：每组 128 个 4bit 码乘上 scale 再加 bias，逐元素还原成 bf16。两边结果应当逐位接近，差只来自累加顺序。kernel 版换掉的不是答案，是谁在算、一份权重被读几遍。

课程的顺序是四步，每一步都保留前一步当对照。

```
Python 解包      mlx.core 逐元素算子, 中间张量往返显存
vanilla kernel   一个线程算完一个输出
matvec kernel    一个 SIMD group 分摊一个输出
tiled kernel     一个线程组把权重块留在片上, 多行复用
```

第一步给出一个可以信任的答案。第二步把同一件事搬到 GPU，形状直白：输出有 `M·K` 个元素，就开 `M·K` 个线程，第 `(i, k)` 个线程读 `A` 的第 `i` 行与 `B` 的第 `k` 行。它慢，但解包、乘加、写回摆在同一段代码里，读一遍就能核对。

第三步按形状分叉。decode 时 `M = 1`，输出只有 `K` 个，`K` 行权重各读一次，没有任何复用。讲义把这一步交给 `quantized_matvec_x4_fast`，理由写得直接：lane 一起分担一条长点积。vanilla 在同样的形状上也能算，只是每条点积由一个线程从头串到尾。

第四步（Day 3）把权重块搬进线程组共享的内存或寄存器，让 `L` 行激活复用同一块权重。这一步对应上一节 cuBLAS 两个函数里 GEMM 的那一套。

四步的差别都落回算术强度那一栏：decode 的 AI 是 1，读一次用一次，能动的只有读取量与读取的组织方式；prefill 的 AI 是 L，同一块权重能用 L 次，能省的是重复读。

Task 2 只写入口与 `eval_cpu`，不写 kernel。这是把接缝与计算分开：入口负责形状契约、dtype 检查和节点构造，不碰显存。先把它单独验过，Task 3 出错时可能的原因就只剩 kernel 一种。这一条是从课程结构推断的，讲义没有这样写。

Python 解包不会因为 kernel 写出来而作废。它留在 `quantize.py` 里当对账基准，`tests_refsol/test_week_2_day_2.py:60-67` 始终直接测它。Week 3 Day 4 换掉的是它的调用方：`QuantizedEmbedding.__call__` 改成一次扩展调用（`tiny_llm_ext.h:36` 的注释），`dequantize_weights` 本身仍然留着。

## Week 2 的四个 Day

四个 Day 各自对应一个由形状决定的瓶颈. 测量只回答两件事: 第一个是不是它, 以及改完之后收益兑现了没有.

| Day | 改什么 | 形状 | 算术强度 | 瓶颈 |
|---|---|---|---|---|
| 2 | 权重读取 | decode `(1,E)@(E,N)` | 1 | 带宽 |
| 3 | prefill 的矩阵乘 | `(L,E)@(E,N)` | L | 算力 |
| 4 | elementwise | `(B,L,I)` 逐元素 | 0.25 | 带宽 |
| 5 | attention 的 S² | `(H,L,S)` 打分 | 取决于 L/S | 两者都有 |

Day 4 的算术强度是 0.25: `silu(x) * y` 这类算子每个元素做一次乘加 (2 FLOP), 读两个数写一个数 (6 字节), 所以每字节 0.33 次运算, 远低于 40. 优化方向只能是少写一遍内存, 也就是融合.

Day 5 的 attention 打分, 每个 `(q, k)` 对做 D 次 FMA, 读 2D 个数, 算术强度是 1; 但输出 `(L, S)` 的矩阵如果物化, 写回的量是 `L·S`, 与计算的比随 S 变化. 分块加在线 softmax 的目的就是永不物化这个矩阵.

## 怎么自己算

拿到一段代码, 三步.

**第一步, 确定主导的数据搬运量.** 问「必须从内存读进来多少字节」. 权重矩阵是 `2·K·N` (bf16), 激活是 `2·M·K`, 逐个列出, 取最大的一项或几项.

**第二步, 数 FLOP.** 一次乘加算 2 次. 矩阵乘 `(M,K)@(K,N)` 是 `2·M·K·N`.

**第三步, 相除, 和硬件的比值比.**

```python
E, V, L = 1024, 151936, 128
peak, bw = 3.2e12, 80e9      # 本机实测, 不同机器要重测

for name, M in (("decode", 1), ("prefill", L)):
    flops = 2 * M * E * V
    bytes_ = 2 * E * V       # 权重
    ai = flops / bytes_
    print(f"{name:>8}  AI {ai:>5.0f}  "
          f"内存 {bytes_ / bw * 1e3:>6.2f} ms  "
          f"算力 {flops / peak * 1e3:>6.2f} ms  "
          f"瓶颈 {'算力' if ai > peak / bw else '带宽'}")
```

```text
  decode  AI     1  内存   3.89 ms  算力   0.10 ms  瓶颈 带宽
 prefill  AI   128  内存   3.89 ms  算力  12.45 ms  瓶颈 算力
```

`lm_head` 这一层, decode 时读 311 MB 权重只做 1.56 亿次 FMA, 需要 3.89 ms; prefill 一次送 128 个位置, 同样读一次权重, 做 200 亿次 FMA, 需要 12.45 ms. 同一个矩阵, 同一份读取, 瓶颈换了一边.

## Day 1 那两个数怎么读

benchmark 给出 `prefill 7.18×`、`decode 34.38×`. 这两个数对应两种不同的机制.

prefill 的 7.18 倍来自「不再拼接整句」: Week 1 每步把整个前缀重新送进模型, 计算量是 `O(S)`; kv-cache 只送新 token, 计算量是 `O(1)`. 省下的是重复计算.

decode 的 34.38 倍来自「不再重算历史」: Week 1 每步为全部 S 个位置重算 k、v, 计算量是 `O(S·E²)`; kv-cache 直接读, 计算量是 `O(1)`. 省下的是重复的投影.

两者都不是「同一个计算变快了」, 是「不再做那些重复的计算」. 这也解释了为什么 profiler 里 projections 占 69.5%: 省掉重复计算之后, 剩下的主要开销就是权重读取本身.

再往下走, Day 2 把权重读取量压到 27%, Day 3 让 prefill 的权重被 L 个位置复用, Day 4 把三次内存往返合成一次, Day 5 不物化 `(L, S)` 矩阵. 四次优化各打一个 `max` 的一项, 或者各消一个必须物化的中间量.

## 这个判据的边界

算术强度只回答「瓶颈在哪一边」, 不回答「能快多少」. 它把问题简化成两个下界取大, 忽略了:

- 缓存. 上面的 M=128 之后带宽掉到 22 GB/s, 就是权重开始命中缓存的迹象. 真实的分层比「内存 vs 算力」两分更细.
- 启动与调度. M=1 的 0.581 ms 里, 有 0.16 ms 不在两个下界之内.
- 指令混合. 一个 kernel 里可能同时有加载、计算、分支, 不同指令争用不同的单元.

但这三条都不改变结论的方向: 在 decode 的 `(1,E)@(E,N)` 上, 时间主要由读权重决定; 在 prefill 的 `(L,E)@(E,N)` 上, 主要由 FMA 次数决定. 判据够用来决定「下一个该改哪里」, 不够用来预测精确的加速比. 精确的数字只能实测.
