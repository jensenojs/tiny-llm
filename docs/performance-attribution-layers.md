# 性能归因的分层依据与它的边界

## 一个和式无法反解

`kv-cache` 跑一次 128 进 129 出的请求，墙钟约 3.8 秒。这个数可以拆开核对：128 次 decode 各 29.2 ms（34.20 tok/s），加一次 128 行的 prefill（1742.20 tok/s，73 ms），两部分都在 `docs/week2-day1-baseline.md` 里。这 3.8 秒里，decode 的每次前向让 28 层轮流做投影、注意力、归一化，缓存从 128 个位置长到 257 个，Python 侧为每一步建图、采样、把结果取回。

这些项的量纲各不相同：一个是一次前向的行数，一个是重复次数，一个是每层的算子序列，一个是字节数，一个是驱动的往返。它们相加得到一个以秒为单位的数，这个和式没有逆。知道总和是 3.8 秒，反推不出其中任何一项。

归因的任务是让一个数字只对应一个原因。做到这一点的唯一办法是先给出一种划分，再把测量结果摊到划分的格子里。划分不能从被划分的数里读出来，测量本身不产生它自己的划分。于是问题变成两个：划分从哪里来，以及凭什么相信这个划分没有漏。

讲义的四视图表回答了第一个问题的一半，没有回答第二个。表里列了四种测量，每一种都真实可用（`book/src/week2-profile-guided.md:40-45`）。这四种的共同点在别处：它们都在这套工具链上可实现，表本身没有说明为什么是四个。列出的四种都测过，没列出的没有任何东西保证不存在。

## 划分从哪里来

按资源划分是性能工程的标准做法。资源是能忙能闲的东西：CPU、GPU 的浮点单元、内存带宽、同步等待。任何一个瞬间，机器的推进速度由当时饱和的资源决定。roofline 模型把这个判断写成 `max(字节数/带宽, FLOP 数/峰值算力)`，本机实测的比值是 3.22 TFLOPS ÷ 79.8 GB/s = 40.4 FLOP/字节，低于它的形状受带宽限制，高于它的受算力限制（`docs/week2-bottleneck-ladder.md`）。这个划分对应真实的物理约束，代价在于资源之间会互相等待。两个资源各自都不到满载，墙钟却远大于任何一个的占用时间，这在有流水线和同步点的系统上是常态。讲义的系统时间线一段给出了直接证据：短对话请求里 GPU 活跃约占墙钟的八成，主线程 CPU 用了 0.07 秒，而 CPU 与 GPU 的时间重叠，两者相加得不到墙钟（`book/src/week2-profile-guided.md:344-347`，讲义给出，不是本机测量）。资源划分分开的是「谁在限速」，它不切分时间区间，所以各资源的占用率不构成对墙钟的一个分割。

按抽象层划分是工程约定。请求、设备、算子、kernel、源码行，这五层之所以存在，是因为这套栈在这五个位置都能放一个时间戳或一个计数器。`mx.eval` 给了一个可观测的图边界，Metal 的 dispatch 给了一个可观测的 launch 边界，Apple 的 profiler 能把成本摊回源码行。换一套栈，例如把算子边界擦干净的融合编译器，或者不暴露 per-kernel 计数的运行时，这些层就消失。抽象层划分有用，它的困难在于不能从第一原理推出：它依赖「刚好这几层是可观测的」这个偶然事实。讲义那张表属于这一类，它是这套工具链的目录。

按组成层级划分，来源是系统实际的构造方式。一个请求由若干阶段组成，一个阶段由若干算子组成，一个算子由若干 kernel 组成，一个 kernel 由若干指令与内存事务组成。每一层的元素个数都写在代码里，可以数：129 次输出里 128 次是 decode，每次 decode 走 28 层，每层七次投影加一次注意力加两次归一化（`docs/week2-day1-profiler-walkthrough.md` 逐一列出 `wq/wk/wv/wo` 与 `w_gate/w_up/w_down`）。这个划分的正当性来自「系统按这种方式拼起来」，而这件事可以从源码读出来，不依赖可观测性。

三者的关系可以压成一句：组成层级回答有哪些层、每层几个，资源划分回答每一层内部时间被哪种物理约束占用，抽象层划分是前两者落到具体工具上的投影。

## 组成链在可改动范围处到头

「有没有第五个、第六个、第一万个」这个问题，在组成层级上有一个可以回答的形式：链有多长，取决于代码有多深，而代码的深度有限。

往下走，链在指令与内存事务处停止。再往下是对 threadgroup 的调度、warp 的发射、缓存行的替换，这些描述硬件在做什么，改代码动不了它们。分层的用途是定位一次改动，改不动的地方就是链的末端。这条停止规则是四视图表没有的：表里第四种视图已经能读到源码行和硬件限制器，但它没有说明为什么读到这里就该停，也没有说明为什么再往下的数字不属于归因的结论。

往上走，链的长度随系统结构增加。只跑单请求的脚本，树的根是请求；连续批处理的服务器，根下面多一层调度，一次前向服务若干个请求，单个请求的时间不再能被单独归属，除非先固定同批的其他请求。讲义那个混合队列就是这个形状，8 个请求、并发 1 与并发 4，墙钟分别是 11.8 秒与 12.2 秒，peak 从 3.37 GB 涨到 3.91 GB（`book/src/week2-profile-guided.md:318-322`，讲义给出）。如果换成按层流水线的执行方式，阶段与设备的对应关系从「都在一张图上」变成「跨设备传递」，又多一层边界。反过来，融合编译会合并层：Day 4 把 RMSNorm、RoPE、SwiGLU 各自融成一个 kernel 之后，算子层与 kernel 层在一段时间内是同一层，两个节点塌成一个。

层数不固定，这是「链的长度由系统结构决定」的实际含义。它同时解释了为什么从四视图表出发得不到完备性：那张表的层数是这套工具链的层数，而系统的层数可以不是这个数。

## 四视图是这棵树上的取数点

把四视图放回组成树，每个视图对应一类节点加一种度量方式。

- 请求时钟取根节点，报总时长与一次内存峰值，除了 prefill 与 decode 的相位切分之外不提供内部结构（`book/src/week2-profile-guided.md:62-110`）。
- 系统时间线取设备节点，报 CPU 与 GPU 在同一时钟上的占用区间，它是唯一能看到节点之间接缝的视图。
- 算子重放取算子节点，在固定形状下报各组时长，它把树剪到只剩一层算子。
- GPU capture 取 kernel 节点，报每个 kernel 的份额、硬件限制器的占用率、摊到源码行的成本，后两项正是资源划分在 kernel 这一层的应用（`book/src/week2-profile-guided.md:210-222`）。

这个对应把表变成推论：一种测量能力，等价于「能在某个节点上取到某种数」。它也暴露表的空档。四个视图都在节点内部取数，没有一个直接测节点之间的等待。时间线看起来像在测接缝，实际是把两个设备的区间画在同一根轴上，接缝表现为一段空白，空白没有对应的量。课程至今不提供时间线的命令（`book/src/week2-profile-guided.md:158-161`），原因在这里：测节点内部只需在节点周围插一次同步，测接缝需要跨设备共用一个时钟，是另一类插桩问题。

## 归属唯一的条件

分层的用处是让归属唯一。每一层的唯一性各有前提，前提不成立时这一层的数字就不能用来做决定。

请求层的归属对象是「这个请求的用户感知延迟」。这一层不能把 prefill 与 decode 合并成一个平均值，因为两者的成本律不同：prefill 的激活是 128 行，算术强度 128；decode 的激活是 1 行，算术强度 1，瓶颈从算力换到带宽（`docs/week2-bottleneck-ladder.md`）。同一份权重上，两者相对 Week 1 的加速比是 7.18 与 34.38，差近五倍（`docs/week2-day1-baseline.md`）。合并之后的数会随输入输出长度的比例漂移，对下一步改哪一处没有指向。

设备层的归属是 CPU 或 GPU，唯一性只对区间成立，对墙钟不成立。GPU 忙、CPU 忙、两者重叠、两者都闲，是四种状态，墙钟是这四种状态时长的和。其中「都闲」那一段不属于任何设备，它是交接失败留下的空洞，在讲义那个例子里约占两成（`book/src/week2-profile-guided.md:344-347`，讲义给出）。把设备占用率相加去逼近墙钟，误差来自这一段。

算子层的唯一性要求形状固定。同一个算子在 256×256 的上下文上比 MLX 的 gather-then-attention 慢，在 256×1024 上持平，在 20×1300 上又慢（`book/src/week2-profile-guided.md:424-430`，讲义给出），所以「这个算子贵不贵」在没有形状的句子里没有真值。重放工具把 `S`、`C` 与 logit 设置写进 `workload` 块，并要求两次重放只有这一块一致才能比较（`book/src/week2-profile-guided.md:140-146`）。要求这一块一致，是为了让两次重放描述同一个对象；算子层的唯一性依赖它。

kernel 层的唯一性最先被编译器破坏。组成树在源码里是一棵嵌套的树：算子调用 helper，helper 调用硬件矩阵指令。编译之后这三层被内联成一条指令流，profiler 把同一批指令的成本同时记在三行上，每行都报 81% 到 100%（`book/src/week2-profile-guided.md:404-409`，讲义给出）。「这个 kernel 里哪一行贵」仍有答案，但答案只在最内层那一行唯一，把这几行相加会重复计数。这也是组成关系在二进制层面不成立的第一处证据：算子与 kernel 之间是编译，包含关系只存在于源码。

## 干扰不在树里

温度降频、别的进程抢 GPU、电源功率不稳、文件缓存冷热、内存分配器抖动、硬件故障，这些不隶属「请求 ⊃ 阶段 ⊃ 算子」这条链的任何节点，它们叠加在每一层上。组成树划分的是「代码做了什么」，干扰是「机器在代码之外还做了什么」，后者对叶子的扰动会沿树向上传播，在每一层都留下痕迹，却没有自己的节点。

所以分层的观测手段无法排除它们，一层也无法。增加视图只增加对被扰动的同一批叶子的观测角度，扰动本身不因此可见。可用的手段只有统计：重复测量、取中位数、跨进程交替、把两个变体放进同一轮跑，让一个慢分钟不会只落在一侧（`book/src/week2-profile-guided.md:108-110`，291-293）。

轮转顺序是「分层工具能对付干扰」这个想法的一个反例。重放工具用四份轮转顺序，目的是让每一组都轮流吃一次冷缓存（`benches/profile_week2_kernels.py:204-246`）。独立探针在同一进程里量了固定顺序与轮转顺序的差：五次独立运行的总和比是 0.97、0.97、1.01、1.11、1.37，同进程重复一次轮转是 0.97、0.98、1.00、1.02、1.21，两组分布重叠，固定顺序的偏差没有稳定符号（`probes/week2/day1/replay_profiler_lab.md`）。轮转原本要防的那笔成本是进程首次 `mx.eval` 的 33.8 ms，warmup 五轮已经把它摊掉。一个为消除顺序效应而设计的分层手段，效果落在运行间漂移之下，连它自己的测量都分辨不出来。

干扰的签名是：代码没变，两次 profile 的答案变了。分层分析的签名是：同一次 profile 内部，某个节点异常大。两个签名互斥。看到第一个签名时，再加一层视图是无效动作，有效的动作是把两次测量放在同一轮里交替跑，或者承认这台机器此刻不适合测。

## 残差的符号说明漏在哪

跨层瓶颈是分层模型失效的信号，具体指某一层的成本下降、端到端没有跟着下降。这个现象只有一个解释：成本转移到了模型没有覆盖的位置，同步点、分配器、编译器插入的类型转换、CPU 与 GPU 的交接。讲义六步循环的第 6 步有一半是为了发现它，并把结果写成三种常见情形：目标组下降且请求变快、目标组下降但请求不动、请求变慢（`book/src/week2-profile-guided.md:296-304`）。

判据可以写得更硬：在父节点上比较子节点之和与父节点自身的时间，看残差的符号。

子节点之和明显小于父节点，说明父节点有一个没有建模的子节点，或者有一段花在接缝上。子节点之和明显大于父节点，有两种来源：重叠被算了两次，设备层是典型，CPU 与 GPU 并行时两个区间相加超过墙钟；或者每个子节点各自带了一次它本来不必付的固定开销。后一种更难发现，因为它的符号与前一种相同，而讲义的表每一项只报自己的数、从不加总，符号问题在讲义里根本不出现。

把已知的固定开销从每个子节点上扣掉，剩下的才是它的工作量。35 段同步那个样本走的是第二条路：总和 4127.91 µs 是真实一步 342.54 µs 的 12.05 倍，每段平均 117.94 µs，与一次 `mx.eval` 的固定开销 112.83 µs 相差约 5 µs（`probes/week2/day1/replay_profiler_lab.md`）。扣完固定开销，每段几乎没有工作量留下，占比 44.4% 落在 pointwise 只是因为它有 16 段。这个 profile 里没有昂贵的工作，昂贵的是 35 次同步，而同步不属于任何一个节点。

## 算例：从一步 decode 的墙钟到一个预测

数字来自本机实测，Apple M4、16 GiB 统一内存、MLX 0.32.0、Qwen3-0.6B、`capacity-cache` checkpoint，输入 128、输出 129、`prefill_logits=all`。其中时间线那一项本机没有测，正文在那一处标出并说明它影响什么。以下按层走一遍，每一步说明它排除了哪种可能。

请求时钟先给出 26.5 ms 一步（`capacity-cache` 的 37.77 tok/s，`docs/week2-day1-baseline.md`）。这一步排除「prefill 是主项」：prefill 用一次 128 行的前向算出第一个 token，之后 128 步各出 1 个 token，decode 占绝对多数。它没有说明这 26.5 ms 花在哪，只给出一个待分解的整体。

时间线本该回答 GPU 在这 26.5 ms 里忙了多久。本机没有做这个测量，课程至今也不提供时间线的命令（`book/src/week2-profile-guided.md:158-161`）。所以这一级在本机是空缺的：GPU 活跃时长未知，任何「GPU 占墙钟几成」的说法在这里都没有数据支撑。缺口影响后面的每一步——份额只有乘上 GPU 活跃时长才能变成墙钟时间，缺了它，预测只能写成式子，不能写成数。这一处留着不补，是因为它恰好标出这套方法在本机缺的那一级。

重放给出四组：projections 16.5 ms / 69.5%、pointwise 5.6 ms / 23.6%、attention 1.2 ms / 4.9%、KV growth 0.47 ms / 2.0%，合计 23.8 ms（`docs/week2-day1-baseline.md`，`capacity-cache:decode:128`，warmup 4、iterations 12）。这个合计与上一步的 23 ms 相差 3.5%。两个数来自不同的插桩：一个来自跨设备的公共时钟，一个来自四组同步计时中位数之和。不同来源给出同一个数，这是一次交叉验证，比同一个数的两种写法有分量。

读份额这一步排除三个候选：attention 与 KV growth 各占几个百分点，做到零也换不来毫秒级以上的收益；pointwise 占 23.6%，是除 projections 之外唯一还有量级的组。排除的意思是它不足以成为下一步，是否重要是另一个问题。

对齐两个总量：23.8 ms 与 29 ms 差 5.2 ms。其中约 0.45 ms 是四次 `mx.eval` 的固定开销（本机单次 112.83 µs，见下段），其余约 4.7 ms 在 CPU 侧。这一步排除「重放总量等于一步的时间」这个等式，同时指出重放的树比请求的树少一个节点：重放从算子开始，驱动与准备不在它的树里，它的根不是请求。

份额到预测之间还隔着一次换算。projections 的 kernel 时间减半，省下 23 × 0.695 × 0.5 ≈ 8.0 ms 的 GPU 时间，墙钟从 29 ms 变成约 21 ms，条件是这 8 ms 的 GPU 节省原样落进墙钟、那 6 ms 的 CPU 时间仍与 GPU 串行。若把份额直接乘在墙钟上再取一半（29 × 0.695 ≈ 20.2，减半省 10.1），墙钟是 18.9 ms。两个预测相差约 2 ms，落在同一 workload 两次运行百分之几到百分之二十的波动之内（`docs/week2-day1-baseline.md` 记录到 prefill 有 ±20% 的样本差），错误的算法在这个尺度上不会被数据当场打回。份额不能当预测的实际含义在这里：错误的暴露方式是「几次改动之后总收益对不上」，它一直等到那一步才现形。

上面三个数是否描述同一个对象，需要单独核对。69.5% 那一组重放的 `workload` 是 `capacity-cache`，`docs/week2-day1-baseline.md` 同一次基准里 `capacity-cache` 的 decode 是 37.77 tok/s，即 26.5 ms，而 29 ms 对应 `kv-cache` 的 34.20 tok/s。若 29 ms 与 23 ms 取自以 `capacity-cache` 为对象的另一次测量，三个数同源；若 29 ms 取自基准表，墙钟与重放分属两个 checkpoint，上面那个 5.2 ms 的差额要按 2.7 ms 重算。讲义与附录要求每次测量把机器、版本与 workload 写在结果旁边（`book/src/appendix-performance.md:296-308`）；同一条要求落在这三个数上，就是先确认它们同源，再谈归属。归属唯一性的第一条要求是参与相减的两个数描述同一个对象，这条要求在这里决定的正是差额该取哪个值。

固定开销这一项需要单独交代它的尺度依赖。0.45 ms 的估计来自玩具模型上量到的单次 `mx.eval` 中位数 112.83 µs；在那个 2 层、E=64、272.8 KiB 权重的模型上，真实一步只有 342.54 µs，四次同步 451.33 µs，重放总和 859.12 µs 是真实一步的 2.51 倍（`probes/week2/day1/replay_profiler_lab.md`）。同一个方法，在玩具模型上四份固定开销是真实步的 132%，份额不可用；在 0.6B 上它是 23.8 ms 的 1.9%，份额可用。尺度扫描把这条边界量成了曲线：E 从 64 到 2048，`4×floor/真实步` 从 134.8% 降到 20.1%，重放/真实从 2.21 降到 1.18（同上，warmup 3、iterations 31，与主表数值不可逐位对齐）。判据可以直接算出来，不需要判断力。

## 依据的强弱不一样

同一天里的两处改动，依据强度差得很远，写账时不能合并成「优化」。

**projections 换成 W4 是强依据。** 重放给出 projections 占 GPU 时间的 69.5%，算术强度 1 FLOP/byte 远低于本机实测的 40 FLOP/字节，两条都来自测量。据此推出「减少每步读的权重字节」，链条完整。

**embedding 按需解压是弱依据。** 它省下的是常驻内存，不进 decode 的每一步，重放看不到它，端到端延迟看不到它。而省下的量在这个规模上也不构成约束：

```
                   0.6B              4B
权重              1.11 GiB          7.49 GiB
词表整表展开       297 MiB           742 MiB
词表占权重          26.1%             9.7%
S=2048 时总占用    17.9%             8.6%
S=32768 时总占用    5.9%             6.2%
```

短上下文时总量本来就小，297 MiB 不构成问题；长上下文时 KV cache 才是大头（S=32768 时 3.50 GiB），词表占比降到 5.9%。在 16 GiB 统一内存的机器上，这两种情形都不会因为少了 297 MiB 而从不可行变成可行。

所以「省内存」在这台机器、这个规模上推不出必要性。这一步的正当理由是另外两条，都不属于性能：

其一，Task 3 要写量化 matvec，需要一个能逐步对照的参考实现；`dequantize_weights` 就是这个参考，它必须自己写，不能调 `mx.dequantize`，否则 kernel 出错时没有可比对的中间量。

其二，`QuantizedEmbedding` 的名字与 `__call__` 的语义都是查表，整表展开再查多做了一件语义没有要求的事。删掉它，代码更短，形状推导更直接（中间张量是 `(1, 2, 128)` 而不是 `(151936, 128)`）。

这两条都成立，但都不能换算成延迟或吞吐。弱依据什么时候会变强：模型更大或词表更宽（4B 的词表是 742 MiB）、内存受限的设备、并发请求让 KV 叠加到逼近上限。那时词表那块的占比才可能从 6% 变成决定性的几个百分点。

## 适用条件与失效情形

这套方法预设成本主要花在组成链的某一层上。预设不成立时，分层给出的结论是「还没找到」，这个「还没找到」与「已经测过、确实没有」在报告上长得一样，这是它最危险的地方。

瓶颈落在跨层同步本身时，链上每个节点都不昂贵，昂贵的是连接。上面 35 段同步的实验是这个情形的一个实测样本，整步时间里同步往返占主导。这时候要动的是同步次数或执行方式，去树里找节点只会得到一个各层都不大的 profile。

外部干扰主导时，profile 在两次运行之间不重复，任何一次分解都只是某一次运行的分解。判据可以量化：同一 workload 连跑两次的相对差超过了你打算检测的效应，下钻得到的就是噪声的形状。

观测期间系统结构本身变化时，测到的树不是运行的那棵树。三种常见来源：动态 shape，同一个算子在一个请求内遇到多个形状（讲义混合队列的 13 个注意力形状，`book/src/week2-profile-guided.md:424-430`）；JIT 重编译，MLX 按形状编译，新形状触发编译，capture helper 先在目标形状上编译并预热，正是为了让 trace 里只有稳态（`book/src/week2-profile-guided.md:199-202`）；内存压力触发的换页与分配失败回收。这三种情形下 profile 没有错，它描述的是另一个对象。

还有一条更隐蔽的前提：分解依赖于「把这一层单独拿出来跑，它的成本不变」。重放的做法正是这样，它重建算子序列、独立计时。这个前提在缓存状态、频率提升、跨组重叠上都不严格成立。本机的量法把偏差归到一处：`重放总和 ≈ 真实一步 + builder 数 × 单次 eval 往返`，残差落在 −8.4% 到 +8.2%（`probes/week2/day1/replay_profiler_lab.md`）。分解的代价是一个加性项，它不随工作量缩放。比例项可以校正，加性项在工作量小于它时无法校正：尺度扫描 E=2048 那一档，attention 与 cache 两组自报的时间里分别有 52% 与 72% 是往返，这两组的份额在各自被测的尺度上都不可用。

## 端到端在方法里的位置

如果目前的判断方式只有端到端验证，即同一 workload 下比较墙钟，这不落后。端到端是唯一能回答「用户感知的延迟变了没有」的观测，其余每一层都是它的代理量，代理量的有效性依赖「这一层的改变会原样传到端到端」这个假设，而上面几节反复在检验的正是这个假设。用代理量做决定时，端到端是仲裁者；缺少仲裁者时，代理量的变化方向没有对错可言。

值得下钻的时机有两个，都由端到端的异常触发。其一，端到端变慢而你说不出为什么，树的用处是给出一个可以怀疑的位置。其二，某一层的改动收益没有出现在端到端上，这是模型漏了一层的直接证据，此时该看的是父节点上的残差，再往下一层没有用。端到端稳定且差异落在噪声之内时，下钻产生的数字没有对应的决定可做：profile 只回答了没有人在问的问题。
