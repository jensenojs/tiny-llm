# 性能诊断中的观测选择与归因边界

性能诊断要支持一个具体决定：面对某个工作负载的延迟或资源约束，下一步改哪里，以及什么结果会使这个决定需要调整。请求时钟、时间线、算子重放和 GPU capture 分别观察执行的一部分；工具清单与分层结构提供入口，选择入口还需要候选解释及其可检验的预测。

## 一个和式无法反解

用 `docs/week2-day1-baseline.md` 的 `kv-cache` 吞吐估算，128 次 decode 约需 `128/34.20≈3.74` 秒，一次 128 行 prefill 约需 `128/1742.20≈0.073` 秒，合计约 3.8 秒。这是由阶段吞吐反算的数量级；一条请求的实际墙钟仍应直接记录。执行中，每次 decode 让 28 层轮流做投影、注意力、归一化，缓存随输出增长，Python 为每一步建图、采样并取得结果。

行数、字节数和调用次数要经过执行机制，才会形成时间成本；成本之间又有依赖和重叠。总时长将这些关系压成一个数，单凭它难以反解内部过程。

同一个总时长可以由多种执行过程产生：较多字节经过一个已繁忙的接口，较少字节经历较长的依赖等待，或者 GPU 很快完成但下一批工作尚未提交。即使取得多个指标，不同原因仍可能产生相近观测。因此归因要构造一条足以解释当前现象、预测条件变化后结果的因果链，再用观测和干预逐步检查。

划分帮助定位“在哪里取数”，并不自动给出“为什么慢”。讲义的四视图表列出了这套栈可取得的几类证据；每一类是否值得使用，取决于它能区分当前哪些解释，以及取得结果后会怎样行动。

## 开放的原因集合与有限的诊断决定

可疑原因会随新事实增加。输入布局、同步方式、编译选择、缓存状态、电源策略和其他进程都可能改变运行结果；事先列出一套工具或组成树，无法证明已经覆盖未来遇到的全部机制。这个开放性使全局穷尽缺少可行的终点，却仍允许围绕当前决定做局部检验。

例如，转置 Axpby 比连续版本慢，可以先提出两条有代码依据的解释：general 增加逐维整数寻址；转置地址使内存系统承担更多服务。两条解释可以同时成立。若当前决定是“先改寻址还是先改布局”，记录更多普通墙钟样本可以检查差异是否稳定，却很难单独区分这两项贡献；捕获实际指令和资源指标能缩小调查范围，固定其中一项的对照才能进一步检验另一项。

即使暂时只考虑这两个已知机制，总时长仍会把它们压成同一个结果。候选全部已知，也可能需要改变实验条件才能区分；测量本身若增加同步，又会改变待解释的执行。原因集合的开放性、有限观测的信息损失和实验对执行的扰动，分别带来不同困难。

因此每轮先说明要改变的决定，再给出当前候选机制、候选之间预测不同的地方，以及成本较低、足以影响决定的观测。结果若与预测不符，就调整机制或测量模型。例如捕获中只有同步命令时，应先检查计算是否进入捕获范围，取得有效 dispatch 后再分析性能数据。

局部收敛可以由明确的验收条件结束：同一目标工作负载下，正确性保持，所改机制按预测变化，端到端收益或资源成本满足要求，并经过适合该效应大小的重复测量。这足以支持当前工程决定；更换规模、版本、负载或目标后，应重新检查原有依据。

## 工具选择取决于候选解释的分歧

若 GPU kernel 已经很快、CPU 准备不足以持续供给，单独把 kernel 做快，对端到端的影响可能很小。若时间主要花在设备内执行，则需要继续检查设备工作。这两条机制对同一时钟上的 CPU 提交与 GPU 执行区间有不同预测，因此此时优先取得时间线。

若已确认执行集中在设备内，但尚未确定应研究投影还是注意力，固定形状的算子重放可以给出候选区域。若已经选定某个 kernel，继续重复同一组算子占比的决策收益会降低；下一项证据可以是实际 dispatch、编译指令、绑定 strides，或相应资源的压力。由当前分歧决定工具，可以跳过与决定无关的层级。

Axpby 的两项解释导出了三组对照：A 为连续输入执行 contiguous，B 为相同连续输入执行 general，C 为转置输入执行 general。A/B 保持输入地址、输出工作量和派发尺寸一致，检查完整实现策略的影响；B/C 固定 general，检查布局变化。A/B 若有稳定时间差，就提高研究实现策略的优先级；B/C 若有较大差异，就提高布局与内存路径的优先级。2026-11-17 已完成这组实验，结果及其如何改变判断见下文。

| 当前待决定的问题 | 需要区分的机制 | 优先观测及其用途 |
| --- | --- | --- |
| 这次变更是否改善目标请求 | 真实收益、工作量变化或运行漂移 | 匹配工作负载，交替重复端到端计时，并核对实际执行内容 |
| 先改主机供给还是设备内计算 | 工作开始前等待较多，或执行本身较长 | 对齐 CPU 与 GPU 时间线，检查等待发生在哪些调用与依赖之间 |
| 哪一组代码值得先调查 | 不同算子组在目标形状下成本不同 | 重放候选组，保留其额外同步与合成输入的测量条件 |
| general 为什么更贵 | 寻址指令与内存服务需求同时改变 | 单 kernel 捕获及资源指标；进一步用固定一项的对照检验另一项 |

## 指标对哪个问题有用

数值能否改变候选解释或行动，决定它对当前诊断的价值。指标的定义、分母、归属范围与采集方式属于读数的一部分。

一个只捕获一个 kernel 的 trace，shader Cost 为 100% 是该捕获的自然结果；它能确认成本归属，却无法在多个优化对象之间排序。general 的 Instructions 为 118、连续为 7，可以检查编译实现确实不同；动态执行次数、指令吞吐及重叠仍决定实际时长。Integer Limiter 衡量对应资源相对于峰值能力的压力，与“整次请求中有多少时间花在整数运算”采用不同分母。

归属到目标 kernel 的末级缓存与外部读取量，可以比较不同接口承担的服务；判断瓶颈还需要带宽、依赖与完成时间。本次 Instruments 的流量覆盖整个 GPU，目标执行期间的增量还需核对背景活动。L1 miss 百分比需要结合请求量和访问代价，单独的较高或较低数值不能给出整次调用的时间贡献。算子重放的 69.5% 则以各组独立计时中位数之和为分母，首先回答该重放中哪组较贵。

## 划分从哪里来

按资源划分可以建立服务能力与工作量的关系，例如内存接口每秒传多少字节、执行管线每秒处理多少运算。roofline 的 `max(字节数/带宽, FLOP 数/算力)` 比较两个资源时间下界。`docs/week2-bottleneck-ladder.md` 的参考测量为 3.22 TFLOPS 与 79.8 GB/s，比值约 40.4 FLOP/字节；在工作量、可用能力与充分重叠等假设成立时，这个交点可以筛选带宽或算术需求较大的候选。小 kernel、依赖链、启动与同步还可能使实际性能远离两个上限，因此算术强度只提供候选约束。

资源压力与时间区间是两个问题。CPU 与 GPU 可以重叠工作，也可能同时等待依赖；未充分供给时，设备即使未满载也会使请求推进缓慢。讲义给出的短对话例子中，GPU 活跃约占墙钟八成，CPU 与 GPU 时间有重叠（`book/src/week2-profile-guided.md`，属于讲义案例）。要解释本机请求，还需本机相同工作负载的时间线。

按观测边界划分，取决于运行时与工具提供什么接口。请求时钟、`mx.eval`、Metal dispatch 和 shader 采样各提供一类边界；编译融合会改变算子与 kernel 的对应关系，源码行分析还依赖采样、符号和内联映射。某个边界可观测时，可以为它设计测量；接口缺失时，需要采用其他能区分候选解释的证据。

按组成关系划分，来源是系统实际的构造方式。源码中可以数出一次 decode 经过 28 层，各层包含 `wq/wk/wv/wo` 和 `w_gate/w_up/w_down` 等调用（`docs/week2-day1-profiler-walkthrough.md`）。这些调用提供寻找成本的入口。运行时还会因融合、分派与循环改变实际 kernel 序列，因此源码调用数要与命令树核对；多个算子也可能共享一个 kernel。

组成关系提供候选工作，资源模型给出工作如何约束完成时间，观测边界决定目前能检验其中哪一部分。三者要相互校对；它们本身也会随编译与执行方式变化。

## 下钻深度由可检验的决定约束

组成树可以继续展开到指令、事务与调度，候选原因也可能出现在代码以外。工程上的停止条件是现有证据是否已足够支持当前决定，以及更深一项观测是否可能改变这个决定。

threadgroup 形状、寄存器需求、同步点与访问布局会影响硬件调度、驻留和缓存行为，因此硬件机制有时直接决定代码设计。继续调查的条件是存在可操作的候选变化，例如调整组形状，并能预测它将改变哪个资源需求。若当前只需确认两个请求是否共享缓存对象，深入 shader 指令通常提供较少的决定价值。

往上走，连续批处理增加了调度与共享工作。每个请求的到达、首 token 和完成时间仍可直接记录；共享计算的成本如何分给各请求，则需要约定归属规则。讲义的 8 请求例子中，并发 1 与并发 4 的墙钟分别是 11.8 秒与 12.2 秒，peak 从 3.37 GB 涨到 3.91 GB（`book/src/week2-profile-guided.md`，讲义数据）。这组总量适合检验该调度配置的总体效果，单请求等待来自哪里还需请求级事件。融合与跨设备流水线同样会改变调用、执行和等待的对应关系。

## 四视图是这棵树上的取数点

把四视图放回组成树，每个视图对应一类节点加一种度量方式。

- 请求时钟取根节点，报总时长与一次内存峰值，除了 prefill 与 decode 的相位切分之外不提供内部结构（`book/src/week2-profile-guided.md:62-110`）。
- 系统时间线对齐主机、设备与同步事件，适合检查工作之间的依赖和等待；应用事件与分布式 tracing 也可记录相应边界。
- 算子重放取算子节点，在固定形状下报各组时长，它把树剪到只剩一层算子。
- GPU capture 保存命令、管线与绑定资源，profiler 重放后可取得 kernel 成本及资源指标。源码行成本还需要对应采样和符号条件，本次 Axpby 只取得 shader 概览及硬件指标。

同一时钟上的提交、GPU 开始与结束事件可以给等待和执行分别计时。本次 Instruments 记录就提供了 CPU-to-GPU latency；其起点是工具定义的 CPU 参照事件，仍需核对它与 Python 调用、编码和提交的关系。时间线中的空白提示活动或覆盖缺口，解释空白还要检查依赖、其他进程与采集范围。课程是否提供封装命令属于工具供给，与等待本身能否观测分别处理。

## 计时与归属需要明确约定

请求完成延迟、首 token 延迟、decode 吞吐与内存峰值服务不同目标。总延迟适合验收整个请求；prefill 与 decode 分开计时适合检查阶段机制。同一份基线相对 Week 1 的 prefill 与 decode 加速比分别为 7.18 和 34.38，说明输入输出长度会改变总收益。二者应随目标一起保留。

对同一请求区间，可按“CPU 与 GPU 都忙、仅 CPU 忙、仅 GPU 忙、两者都未记录到活动”做互斥分割。CPU 时间与 GPU 时间直接相加则会重复计算重叠部分。“GPU 活跃占八成”只给出 GPU 的活动覆盖；剩余两成中还可能有 CPU 工作、依赖等待或采集缺口，需要对应事件才能解释。

算子比较先固定要保持的工作量，再核对 shape、dtype、布局、实现与状态。讲义的注意力案例在不同形状下出现相对优劣变化，说明排序随条件变化。实验若有意改变形状或布局，应将它列为自变量，并解释输出工作量是否仍可比。

源码行归属还依赖工具如何累计内联成本。讲义给出的多行 81%–100% 属于可能重叠的归属视角，逐行相加会重复计算。选择某一行修代码前，要核对底层指令、映射方式与动态路径。明确 inclusive、exclusive、采样份额和归属范围，可以使这些数服务调查，而不必强求每个成本都唯一对应一行源码。

## 运行状态也进入候选模型

温度与频率、其他进程、缓存状态、分配器和编译状态都可能改变节点成本。组成关系通常没有表达这些变量，遇到跨运行漂移时可以把它们加入候选。温度、频率、其他 GPU 活动、分配及缺页事件在工具支持时可直接观察；重复与交替测量则帮助估计漂移、降低执行顺序与变体的混杂。

历史探针中，固定顺序与轮转顺序的五次总和比为 0.97、0.97、1.01、1.11、1.37；同进程重复轮转的比为 0.97、0.98、1.00、1.02、1.21（`probes/week2/day1/5_replay_profiler_lab.md`）。该样本显示运行漂移与顺序差异处在相近尺度，尚不足以把变化独立归给冷缓存。warmup 处理首次执行效应，轮转平衡组在轮次中的位置；两者控制不同变量。

跨运行漂移与某个节点较贵可以同时出现。此时选择同时记录节点行为与运行状态，或先用交替实验确认效应大小。若信号仍被波动覆盖，可以增加配对样本、控制环境或选择扰动更小的事件；报告应保留目前能分辨的差异范围。

## 残差首先检验测量能否相加

目标组变快而端到端近似不变，至少与三种机制相容：目标工作原本与另一项重叠，收益被较慢路径遮住；变更使另一项成本增加；收益存在，但小于当前测量能分辨的变化。重放与真实执行条件不同还会造成第四种情形：目标组只在重放条件下变快。它们分别需要时间线、完整执行内容或重复实验，单凭这个结果尚不能选择原因。

父子时间求差之前，先确认它们来自相同调用和时钟范围，并处理重叠、插桩成本与统计汇总方式。若对子区间做了互斥分割，剩余时长可以定位尚未覆盖的区间；若各组独立重放，差值还混入了缓存、工作量与提交方式的变化。

即使调用与区间都一致，统计汇总也会制造残差。构造三次串行调用，子项 A 的时长为 `[1,10,10]`，B 为 `[10,1,10]`，父项逐次为 `[11,11,20]`。子项中位数相加为 20，父项中位数为 11。每次都完全覆盖、完全串行，九个单位的差来自中位数的非加性。重放总和与真实步中位数求差，首先要面对这类问题。

历史玩具实验把一次 forward 切成 35 段并逐段同步，分组中位数之和为 4127.91 µs；单次求值的真实步中位数为 342.54 µs，前者约为后者的 12.05 倍。独立短算子往返的中位数为 112.83 µs，与分段总和除以 35 所得的 117.94 µs 接近。这支持“逐段同步显著改变了被测执行”的判断。

`5_replay_profiler_lab.py` 的 `measure_floor()` 实际计时包含一次 64 元素加法及其求值。这个短算子往返只能作为当次环境的开销量级参照。直接从每段减去同一个常数，会把开销恒定、可加以及插桩后工作成本不变当成前提；现有实验尚未独立验证这些前提。校准应通过改变同步次数、保持目标计算一致的对照检验，必要时改用设备事件取得原执行的区间。

## 算例：从一步 decode 的墙钟到一个预测

这里使用历史本机记录：Apple M4、16 GiB 统一内存、MLX 0.32.0、Qwen3-0.6B，输入 128、输出 129、`prefill_logits=all`。`capacity-cache` 的 37.77 decode tok/s 对应整段 decode 平均每 token 约 26.48 ms；`kv-cache` 的 34.20 tok/s 对应约 29.24 ms。固定 checkpoint 是比较的第一步，整段 decode 还包含随生成增长的上下文。

同一记录中的 `capacity-cache:decode:128` 重放固定缓存长度，warmup 4、iterations 12。四组中位数依次为 projections 16.5406 ms、pointwise 5.6074 ms、attention 1.1746 ms、KV growth 0.4739 ms，合计 23.7965 ms。重放排序把投影列为优先调查候选。它采用合成输入、组间独立求值；上述 26.48 ms 则来自整段请求的吞吐。即使 checkpoint 一致，两者仍描述不同执行，直接相减得到的约 2.68 ms 尚无 CPU 或 GPU 的唯一归属。

仓库已有 `probes/week2/day2/step_timeline.py`，在 Python 侧将单步分成 model 调用、`mx.eval(logits)` 和采样三段。源码显示采样段也有 `mx.eval(nxt)`；eval 段则包含提交与等待。因此该脚本可以检查主机侧阶段耗时，输出的“GPU 占比”标签应读作 eval 调用墙钟占比。要取得 GPU 真实活动与主机重叠，需要设备时间线。本算例的历史表尚未提供与其匹配的这类记录。

下一项实验由当前决定产生。若要选“先改主机供给还是先改投影”，应在目标形状上取得时间线。若已准备验证 W4 投影候选，则可比较投影重放，并回到同一端到端 workload 验收收益：重放下降而请求近似不变时，检查重叠、真实分派和其他成本。原记录的 prefill ±20% 波动只约束那个测量，decode 的可分辨效应需要它自己的重复样本。

预测还需显式的时间模型。假设匹配的真实调用总时长为 T，其中串行关键路径上的投影耗时为 C；若只把 C 加速到二分之一，其余工作及重叠关系保持，则 `T_new=T−C/2`。要把重放的 16.5406 ms 代入 C，需要另行验证它代表真实路径上的可缩短区间。69.5% 首先只是这份重放的份额。

玩具模型的尺度扫描提供另一项检查：E 从 64 到 2048 时，重放/真实步由 2.21 降至 1.18，短算子往返相对于计算规模的重要性随之变化。它提示优先检验小工作量上的测量扰动，仍需核对真实实现、缓存和提交方式，才能决定重放排序对当前优化是否足够可靠。

## Axpby 将流量、执行资源和完成时间分开取数

Axpby 提供了一个工作量足够明确的归因实例。比较两个 `4096×4096` float32 输入：连续组计算 `x+y`，转置组计算 `x+y.T`。两组各产生同样数量的输出，区别在于 y 的地址排列和所选实现。连续 kernel 直接用 index，general 需要用 shape 与 strides 把逻辑下标转换为元素偏移。

先从源码建立流量假设。若按对齐的 32 字节块获取，连续的 32 个 float32 覆盖四块，转置布局同一批请求覆盖 32 块，y 的局部块数比为八倍。完整计算中，后续输出行会消费同块的其他元素，实际获取量取决于块在哪层保留。若在某个接口处 y 由一次完整读取放大到八倍，同时 x 读和 out 写各为一次，则总量从 `64+64+64=192 MiB` 变为 `64+512+64=640 MiB`，比值为 3.33。这里块大小、每块获取次数与 x/out 的流量均为指定的模型条件。

在某层缓存保留数据、向更近请求方重复提供的情形中，内部服务可以放大，外部取回的数据仍保持较少。固定输出列 c，转置组的第 0 至 7 行读取原 y 偏移 `c*4096+0` 至 `c*4096+7`，这些不同元素在该模型中共用一块；如果较近缓存未保留、末级缓存保留，八次请求可以分别由末级缓存服务，同时复用外部取回的数据。这个地址关系说明具体复用对象，实际命中位置仍由硬件观测决定。

2026-11-16 本机对该 bench 录制 Instruments Metal System Trace，按目标进程 99 个 encoder 的创建顺序识别三组 `3 次预热+30 次测量`，再通过 encoder ID 关联 GPU 执行片段。计数器带宽样本与目标执行区间求交集，逐段执行“带宽乘时长”，得到服务量。100 GB/s 持续 1 ms 为 100 MB，200 GB/s 持续 2 ms 为 400 MB，两段合计 500 MB；每组积分再除以 30，得到平均每次的数据量。百分比计数器则按交集时间加权。

| 测量与范围 | 连续组 | 转置组 | 转置/连续 |
| --- | ---: | ---: | ---: |
| 普通运行，30 次平均墙钟 | 2.6020 ms | 3.0463 ms | 1.17 |
| Instruments，30 次平均 GPU 活跃时间 | 3.7059 ms | 4.0887 ms | 1.10 |
| 同次 Instruments，末级缓存服务量积分 | 250.16 MB | 1094.75 MB | 4.38 |
| 同次 Instruments，GPU 外部读取量积分 | 155.70 MB | 152.98 MB | 0.98 |

末级缓存指标实际名为 Last Level Cache Bandwidth，定义为 GPU 末级缓存读写速率；外部读取指标为 GPU Read Bandwidth。目标执行期间，全 GPU 的末级缓存服务量增加，外部读取量接近，这支持继续调查内部重复服务。原始记录的 scope 为“Whole-GPU samples clipped to target GPU intervals; mixed-process traffic”，包含同期其他程序；先核对背景活动，才能进一步判断增量有多少来自 Axpby。表中 MB 为十进制，前面模型为二进制 MiB。3.33 的模型比值与 4.38 的采样比值描述不同前提下的量，前者还需要真实事务规则和工作归属来验证。

流量 Q 只有在结合该资源可提供的带宽 B 时，才产生 `Q/B` 的服务时间下界。还要把它与整数指令、浮点指令及依赖链的需求比较，考虑各项重叠。实际平均速率 `Q/T` 是观测结果：本次末级缓存两组约为 67.5 GB/s 与 267.8 GB/s，因而 4.38 倍服务量与约 1.10 倍时间可以相容。用这个观测速率代回 Q/B 只会还原 T；独立判断瓶颈需要资源能力依据或受控变化后的结果。外部取数增加时也应先检查外部接口是否成为限制资源。

为将整数压力接到实际实现，2026-11-17 又在同机用 `.gputrace` 捕获预热后的一个 Axpby，并用 gpudebug 重放，两种布局分别捕获、分别保存一次 profiling session。命令树核对到实际 `axpby_contiguous_float32` 和 `axpby_general_float32`，各一次 dispatch；general 的参数实读为 shape `(4096,4096)`、strides `(4096,1)` 与 `(1,4096)`、ndim 2。

| 该次单 kernel 重放 | 连续路径 | general 路径 |
| --- | ---: | ---: |
| GPU time | 2.2706 ms | 3.5630 ms |
| shader Instructions | 7 | 118 |
| shader INT32 | 0 | 24 |
| shader Temp registers | 3 | 16 |
| Integer and Complex Limiter | 0.00% | 63.85% |
| Last Level Cache Limiter | 31.17% | 65.56% |

general 的整数除法、取余与偏移乘加要求更多执行指令。shader 概览显示编译实现形状，Limiter 描述对应管线相对于峰值能力的压力，100% 表示该管线达到容量上限。63.85% 的整数压力支持检查寻址需求；它与“63.85% 的时间花在寻址”具有不同分母。缓存压力同时上升，独立贡献需要进一步固定寻址或地址布局做对照。

单 kernel 重放比值约 1.57，属于另一次 GPU profiler 采集，条件不同于 30 次采样和普通秒表；它可以验证具体实现的指令与资源需求，端到端收益仍需回到匹配的普通运行。当前重放报告为 3 sampled / 10 total cores，各 trace 一次 session，尚未提供重复测量范围。

复跑的最小路径如下，命令在仓库根目录执行：

### 三组对照怎样改变调查优先级

原来的连续与转置两组同时改变实现与布局。新入口 `probes/week2/day1/4_axpby_control.mm` 加载同一份已编译的 metallib，增加连续输入执行 general 的 B 条件。三个条件共用输入及输出缓冲、`4096×4096 float32` 工作量和 `1024×1×1` 组尺寸，以直接 Metal 派发取得 GPU 时间。MLX 建图与分配位于另一条计时边界。

| 条件 | 普通进程 run1，GPU 中位数 | 普通进程 run3，GPU 中位数 |
| --- | ---: | ---: |
| A：连续布局＋contiguous | 2.1767 ms | 2.1459 ms |
| B：连续布局＋general | 2.2156 ms | 2.1415 ms |
| C：转置布局＋general | 2.7268 ms | 2.6907 ms |

每组预热三次，正式测量六十次，按六种排列轮换。B/A 分别为 1.0179 和 0.9979，C/B 分别为 1.2307 和 1.2565；二十个六轮区块中，C 都比 B 慢。当前规模下，布局变化给出更清楚的完成时间信号，调查优先级因此转向布局及内存访问。输入和全部样本保存在 `docs/evidence/axpby-controls/`。

三份单次 profiler 重放又取得 A/B/C 的 Instructions 为 7/118/118，Integer and Complex Limiter 为 0.00%/85.16%/66.06%，末级缓存 Limiter 为 30.73%/14.05%/66.94%。B、C 使用同一份 general 编译代码，C 执行更慢却有更低的整数 Limiter；这个结果要求把资源压力与完成时间分别解释。普通派发中的 A/B 接近，也使“指令数相差十余倍就应先改寻址”缺少时长依据。

profiler 的 A/B/C 时间为 2.3132/2.6910/3.4527 ms，采样覆盖分别为 6/4/5 个核心；重放时的缓冲初态与普通计时不同。profile 的 B/A 约为 1.16，普通计时约为 1，正好暴露出观测条件的重要性。优先级判断采用当前普通重复测量，profile 用于核对实现与资源线索；完整表格、API 校验、正确性覆盖及复跑路径集中保存在 `docs/metal-counter-investigation.md` 的三组对照一节。

本轮已足够支持下一项工程选择：遇到同类布局问题时，先调查访问方式；进入真实推理工作负载时，将布局准备、额外内存和复用次数一起计时。若继续追问额外整数工作怎样被重叠，需要另做规模变化与执行依赖的对照。这个问题扩展硬件理解，是否继续应由课程当前需要的决定来约束。

## 证据强度相对于目标判断

投影重放占比较大，加上每步需要读取大量权重，为 W4 投影提供了可检验的候选：减少权重字节是否会降低真实投影成本，并传到请求时间。解量化指令、实际分派和数值精度也随之进入模型。该候选的依据比“某个实现看起来更短”充分，收益仍应由匹配实验建立。

embedding 按需解压则可能服务于常驻内存、初始化时间或每步查表成本，需要分别测量。一个 `[151936,1024]` 的 bf16 整表约为 297 MiB，`[151936,2560]` 约为 742 MiB，由元素数乘两字节得到。省去整表驻留能直接减少这部分数据的存储需求，真实进程峰值还受共享、分配器及生命周期影响；逐次解压又会增加执行工作。仅看 decode 秒表，无法判定这项内存取舍是否满足目标。

若当前目标是降低 decode 延迟，应记录每步查表、解压与缓存影响。若目标是让整个工作集装入设备，或增加可承载并发，则应检查实际峰值、KV 增长、其他驻留数据及安全余量。相同的 297 MiB 在不同目标下可以有不同价值。

实现可独立对照的量化参考、简化查表语义，也可以是教学或维护目标。将这些目标与延迟、容量分别陈述，可以选择相应验收证据，避免把代码形式直接换算成性能收益。

## 新事实如何改变模型

逐段同步使整步显著变慢，说明测量方式已经改变执行。可以将同步次数列为实验变量，保持计算内容一致，检查总时长如何随它变化。对原执行的判断应同时保留单次求值基线。

若同一配置的运行漂移大于待验证收益，应先估计差异的分布及其与顺序、温度或背景负载的关系。单次 profile 仍能确认某次实际执行了什么；跨运行的细小耗时排序则需要更多依据。根据待解释的问题选择事件或配对实验，有时比继续增加相同的总量样本更有效。

动态 shape、新实现首次编译与内存压力事件，会使请求经历多种状态。若目标是稳态吞吐，应分别标记首次执行并匹配后续形状；若目标是冷启动，则编译与初始化本身属于目标工作。预热的选择由目标决定。

独立重放会改变缓存、频率、依赖和提交方式。玩具实验中“重放总和接近真实步加若干短算子往返”是一项样本关系；它值得通过保持目标计算、改变分组的实验继续检查。将它推广为通用校正式，或据此宣布某个百分比以下即可采信，需要额外证据。

报告可以将每个结论写成可复核的状态：已观察到哪些事件、采用哪条机制解释、哪一步由条件推导，以及下一项结果会使解释调整。这样新事实进入时，可以准确修改断裂处。

## 端到端在方法里的位置

端到端测量直接检验目标工作负载的完成效果，内部观测帮助解释效果怎样产生。目标包含首 token、尾延迟、吞吐或峰值内存时，验收应分别对应这些指标。内部优化传到端到端的关系，由关键路径、重叠和其他成本共同决定。

调查可以由回归、容量规划、预测未来规模，或评估一条实现路线触发。即使当前端到端稳定，只要下一项观测会影响一个有价值的决定，就有继续调查的理由。若候选优化的收益、风险与验证成本已经足以比较，则可选择实施、保留现状或停止该方向。调查深度应随这个决定的价值收敛。
