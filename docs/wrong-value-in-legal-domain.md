# 错误在哪一层失去位置信息

真机输出乱码。这就是全部观测。

乱码能表达的东西只有一件：收到的字节不是合法文本。它不能表达这些字节是谁给的。这一层没有表达来源的语言——就像拿着一份坏掉的文件，文件本身不会告诉你它从哪个目录来。

所以“看见故障”和“能定位故障”是两件事。前者取决于有没有东西报错，后者取决于报错的那一层能不能表达来源。这一轮里，出错的层在掩码构造，显示异常的层在屏幕，中间隔着整条链。

## 检查是一次折叠

中间那些层都有检查：id 数组有 dtype，张量有形状，加法有类型，全过了。

因为检查的方式是折叠：把一个 $2^{64}$ 的值空间按等价类商掉，再看这一类属于合法还是非法。所有 `int64` 折成同一类“合法数值矩阵”，于是 `int64` 里哪个值对类型检查器都等价。输出也只有两个值。

但这不意味着离散的 `if-else` 检查本身抓不住错。任何有用的守卫抽出来也是一个从大空间到“通过/拒绝”的二值切分；它和类型检查的差别不在终点是二值，而在切割的方向。

遮蔽这个语义只有两态：看，不看。语义的基数是 2，承载它的类型基数是 $2^{64}$，差额就是错误值的容身空间。基数越接近，容身空间越小；两者相等时，错误值与正确值不可能同属一类。当承载空间远大于语义空间时，检查器这一刀怎么切决定了能不能看见错：类型检查（`dtype: mx.Dtype`）按“是不是一个合法的 `Dtype` 对象”竖着切，`int64`（错值）和 `float32`（对值）被折进同一个通过类；入口语义守卫（`if not mx.issubdtype(dtype, mx.floating): raise ...`）同样是离散的二值 `if-else`，但它按“能不能承载 `-inf`”横着切，把整型和浮点型分进两个不同的等价类。

损失发生在折叠那一步，不在二值判定那一步。只要切割边界与语义边界正交，错误的值与正确的值就会被折进同一个等价类，检查器就看不见它。“落在合法域”描述的是结果，“等价类重合”描述的是机制。

真正的分野发生在离散语义边界与下游连续数值域之间。在上游构造掩码的入口，“类型是否支持 `-inf`”是离散且边界分明的，补一刀方向正确的 `if-else` 就能把错值切出去；一旦上游没拦住，让 `-inf` 被铸成 `0` 混进下游 28 层连续的浮点矩阵运算里，算子面对的就是整个连续实数空间。在连续浮点空间里，被污染算歪的 `2.31` 和正确的 `-1.85` 都是合法的有限浮点数，下游算子单看手里的张量，已经画不出一条不依赖外部参考答案的局部 `if-else` 分界线来切开对错了。

分辨率由此而来：分辨率是折叠的粒度，错误幅度低于粒度就不可见。类型是分辨率最低的检查，一个 bit，而语义错误通常落在它下面。

这同时给出“测试通过”的含义：错落在了断言划定的等价类里。

调试上的推论有先后：一旦错误滑进了下游连续数值域，单点的二值判定已经切不开对错，就必须先测量，后判定。测量保留连续分辨率（`max|Δ| = 22.4`），二值判定把分辨率丢掉（通过）。拿着参考实现逐层算激活值最大绝对差，拿到 `0.0`（单跑各层）与 `22.4`（顶层串联）两个连续数值，断口当场显形；换成只看“崩没崩、形状对不对”的二值判定，就只剩两个“通过”。

写下来的结论也是折叠。把一段带维度的经验压成一条一维规则（“别用 `inputs.dtype`”），换个形状的问题就会失效，因为压掉的正是“为什么会这样”。能带走的只有结构：切割方向、等价类、合法域稠密度、分辨率。

## 两个例子是同一机制

早年遇到过另一个故障：MySQL 实例同时开着数据面端口和控制面端口，配置时手滑拿控制面端口去连了数据面客户端。正向看只是拿错了一个端口号的低级失误，逆向面对终端时却卡了很久——客户端要么死等不动（阻塞），要么吐出一堆乱码。

拿控制面的端口连数据面的服务，下游收到字节。字节不是合法的数据面协议头，但拆包器按数据面格式去读长度字段时，那几个字节可能碰巧读出一个荒谬的大整数（客户端死等一个永远不来的后续包，表现为阻塞），也可能读出一个落在本包范围内的合理长度（把控制面报文切出来当业务字符串，表现为乱码）。

`dtype` 拿错是同一件事：`causal_mask(L, S, inputs.dtype)`（`src/tiny_llm/qwen3_week1.py:349`）从索引数组取 `dtype`，`-inf` 在整型里铸成一个合法整数，加法照算。

两者的共同点是：正向发生时，控制面端口与数据面端口都是 `int`，索引数组类型与激活值类型都是 `mx.Dtype`，两个属于不同语义平面的值共享了同一个底层类型，单行语法看不出拿混了；逆向暴露时，错误都已经穿过中间层，变成了末端没有来源坐标的阻塞或乱码。

两者的差别只在下游合法域的稀疏度。协议握手头的合法集合（魔数、版本号、状态位）在字节空间里极稀疏，外来的字节流大概率撞在合法集合外面，只要握手层做了校验就能当场拒绝；而 `int64` 与浮点矩阵加法的合法集合就是整个数值空间（稠密度 100%），没有握手这一说，错误必然落在合法域里面，每一层都放行。

端口那个如果能在握手层报错，幸运不在错误小，在暴露的位置信息密度高——握手边界上还留着版本号、包长度这些能反推来源的字段。早报错是早暴露。一旦滑过握手落进后面的字节流读取，位置信息就和 `dtype` 一样被抹平了。

`dtype` 那个从头到尾没有握手。掩码里每个数都合法，形状也对，一路到屏幕上才变成乱码，中间没有任何一站会拒绝它。

这个 bug 落得格外准。`-inf` 在三种 `dtype` 里都铸成合法整数：`int32` 得 `INT32_MIN`（`-2147483648`，加在注意力分数上经 softmax 仍接近 0，首步侥幸蒙混过关），`int64` 与 `uint32` 得 `0`。同一个语义错误在不同合法域里变形为不同的合法值，错误被翻译了一次，没有被拒绝一次。而 `0` 在加性掩码里正是“不屏蔽”，翻译完连含义都反转。

## 错误不住在任何一行里，直到用代码把关系钉进单行

判错边界的 `if` 写错了，错误就在那一行，孤立看它就能说“这里该用 `>=`”。`causal_mask(L, S, inputs.dtype)` 孤立看完全正确：语法对、类型对、linter 不报。错的是它引用的对象与浮点打分之间的对应关系。

于是分两类：控制流错误违反的是一元局部性质，读到那行的人不需要上下文就能判定；值域与平面错配违反的是跨对象的关系（掩码的 `dtype` 必须与注意力分数同域，客户端连接的端口必须与服务端协议同平面），判定它需要同时知道两个对象的语义。在未设防的代码里，没有任何一站同时握着这两份知识——调用点只看到两个合法的 `mx.Dtype`，掩码函数只知道“要个 `dtype`”，不知道这个 `dtype` 是从索引数组上摘下来的。

名字是唯一能携带来源的语法手段。`inputs` 承诺的是“输入”，掩码真正的约束是“与浮点侧同域”。名字隐瞒了约束，错误连“看起来可疑”的机会都没有。

那为什么说“把这类错误防住也只是加一行代码的事”？因为加防御代码或改接口签名的本质，就是把原本悬浮在两个对象之间的隐式关系，物化到同一个语法节点（单行代码）里，让跨对象的关系退化为单行即可判定的约束。

## 方向只剩上游

一旦错误跨过入口滑进稠密的下游，下游每一站都会说这个值合法，往下游追是白追。方向只能朝上游：找最后一个可以确认交接正确的点，站在那个点上问下一段。

这是 C 段在这类故障上的形态。区别在于控制流 bug 的确认点可以靠读代码建立，值域 bug 的确认点必须自己跑——因为“这个值是哪个对象给的”只在运行时存在，读代码时它已经退化成一行表达式。

而在上游写代码封口时，能封的位置有三处，分别用一行代码把悬浮的约束钉死在不同层级：
可以把掩码改成 `bool` 矩阵配 `mx.where`。`bool` 的基数是 2，与“看/不看”的语义基数相等，错误值在类型空间里无处容身，改动面也最大。
也可以在 `causal_mask` 第一行加 `assert mx.issubdtype(dtype, mx.floating)`。加性掩码里 `-inf` 是唯一代表屏蔽的值，整型里根本不可达；这一刀方向正确的离散 `if-else` 把“入参类型必须能表达 `-inf`”钉在函数入口，解决“屏蔽能不能被表达”，但还管不到“是不是拿了另一个浮点张量的精度”，因为浮点域内部依然有多个类型。
还可以把参数从裸 `dtype: mx.Dtype` 换成 `like: mx.array`（传 `like=h`），或者直接在注意力内部取打分张量的 `dtype`。裸 `mx.Dtype` 擦掉了类型是从哪个张量身上取来的来源信息；传 `like=h` 把“掩码与激活值同源”直接焊进函数签名，离散索引数组的类型从语法上就传不进来。

三处封的是三个不同的口：类型的基数、屏蔽值的可达性、值的来源。它们做的都是同一件事——不让跨对象的语义关系悬在半空。

## 现在的位置

手上有乱码一个观测，链路上还没有一个自己确认过的点。

```
prompt 文本 → encode → ids ─┐
                            ▼
                    model(ids) → logits → softmax → sampler → 新 id ──┬─→ detokenizer → 屏幕
                            ▲                                         │
                            └────────── 拼回句尾 ─────────────────────┘
```

它不是一条线，是一个带回边的环。每一圈都把整句重跑一遍，所以第二圈的 `ids` 已经是 `concatenate([原 ids, 新 id])`：新 id 来自 `argmax`，返回 `uint32`，和 `int32` 拼完升成 `int64`。按线性链条往上追，只能追到第一圈；第一圈是好的，变化在回边上。

末端只给类别，不给位置：屏幕上全是合法字符、进程没崩，说明每一站都返回了值；头一个字符像正常开头、第二个起崩，把范围压到第一次产出之后。第一步仍是往上游立第一个确认点：id 数组是不是参考实现的那一串。
