## 第一部分：测试基建

### 1.1 `with mx.stream(stream)` 是什么

`stream` 是 MLX 的**计算流**概念——运算在哪个设备（CPU/GPU）上执行。
测试基建里 `AVAILABLE_STREAMS = [mx.cpu, mx.gpu]`，`with mx.stream(stream)` 让上下文里的操作跑到指定设备。

它和"流式输入""嵌入"没有任何关系。parametrize 会让每个测试在 CPU 和 GPU 各跑一遍，验证实现不依赖特定硬件。

### 1.2 parametrize 笛卡尔积机制

`@pytest.mark.parametrize` 装饰器**不执行任何循环**，它只是往函数上贴一个标签（mark），
记录"这些参数名、这些参数值"。真正的展开发生在 pytest 的**收集阶段**，由 `pytest_generate_tests` hook 完成：

1. 收集阶段扫描 `test_` 开头的函数，生成测试项（test item）。
2. 发现 parametrize 标记时，对多个标记做**全组合（笛卡尔积）**，每个组合生成一个独立的 test item。
3. 执行阶段逐个运行这些 item，每个 item 把一组参数值传给函数。

实证（`--collect-only` 输出）：`test_task_2_linear` 一个函数定义展开成 4 个独立 item：

```
test_task_2_linear[f32-cpu]
test_task_2_linear[f32-gpu]
test_task_2_linear[f16-cpu]
test_task_2_linear[f16-gpu]
```

全文件共 44 个 item：softmax 4 + simple_attention 16 + scale_mask 16 + linear 4 + mha 4
（attention 类测试多乘 `batch_dimension` 的 4 种）。

每个 item **独立执行、独立统计**。之前看到的 `8 failed` = linear 4 份 + mha 4 份，是同一个桩的独立重复。

### 1.3 `batch_dimension` 参数化的特殊性

`stream`/`precision` 传的是**直接可用的值**（设备对象、dtype 对象），测试体直接用。

`batch_dimension` 传的是**索引 0/1/2/3**，测试体自己用 if-elif 查表翻译成实际形状：

```python
if batch_dimension == 0: BATCH_SIZE = ()
elif batch_dimension == 1: BATCH_SIZE = (2,)
elif batch_dimension == 2: BATCH_SIZE = (2, 3)
elif batch_dimension == 3: BATCH_SIZE = (2, 3, 3)
```

即参数化的是一个"配置选择器"，不是直接数据。也可以直接参数化形状本身，两种写法展开结果一样。
值得记住的模式：**parametrize 的值不一定要直接用，可以是索引，函数体内再做查表或翻译。**

多维 batch 的意图：逼实现用负数轴（`-1`/`-2`）和 `swapaxes` 处理，不写死"第 0 维是 batch"。

### 1.4 assert_allclose 精度策略

比较器核心逻辑：

```python
if a.dtype == mx.bfloat16:
    a = a.astype(mx.float32)      # bfloat16 升 float32 再比
...
if precision == mx.float32:
    rtol, atol = 1.0e-5, 1.0e-6   # 严格
elif precision == mx.float16:
    rtol, atol = 5.0e-2, 1.0e-3   # 宽松
```

- **bfloat16 为什么升 float32**：bfloat16 尾数 7 bit，量化台阶约 1e-4，直接比较会被量化噪声淹没。
  实证：`0.1` 存进 bfloat16 变成 `0.10009765625`。升到 float32 后量化台阶消失，比较才有意义。
- **f16 为什么宽松**：float16 尾数 10 bit。两个独立计算路径（用户实现 vs reference）在 f16 下
  同一个值可差 0.55%。用 f32 容差判它会误报，用 `5e-2`（5%）才合理。这是"不掩盖真错、容忍浮点噪声"的折中。
- **容差为什么跟着 precision 走**：浮点误差预算由运算精度决定，所以测试每个都带 `precision` 参数。

### 1.5 rtol 和 atol 的本质

`np.allclose` 的判定公式：


```
|a - b| <= atol + rtol * |b|
```

- **rtol = relative tolerance，相对容差**：比例，无量纲。允许误差达到 `|b|` 的 rtol 倍。
  大数 1000 允许差 0.01，小数 0.5 只允许差 5e-6。
- **atol = absolute tolerance，绝对容差**：绝对量，有量纲。不管数值多大，误差允许达到固定量。
- 两个数**不同性质**，不能互相换算。

为什么加法并两个：浮点误差随值的大小成比例增长（要 rtol）；但 `|b|` 接近 0 时 `rtol*|b|` 趋近 0，
任何误差都超限（要 atol 兜底）。`|b|` 大时 rtol 主导，`|b|` 小时 atol 主导。

### 1.6 refsol 机制

`tests_refsol/` 是测试的**权威源**，`tests/` 是工作副本。`pdm run test --week X --day Y` 每次执行：

1. `copy_test(force=True)`：把 `tests_refsol/test_week_X_day_Y.py` 强制复制到 `tests/`，覆盖本地修改。
2. `pytest -v tests/test_week_X_day_Y.py`。

含义：**只能改 `src/tiny_llm/` 的实现来让测试通过，不能改测试本身**。
因此**不要往 `tests/test_week_*_day_*.py` 写持久注释**（每次跑都会被覆盖）。
安全落点是 `tests/utils.py`、`tests/tiny_llm_base.py`、`scripts/dev-tools.py`（不在复制范围）。

`tests/tiny_llm_base.py` 只有一行 `from tiny_llm import *`——这是 API 契约：
测试里直接调用的名字（`softmax`、`linear`、`SimpleMultiHeadAttention` 等）必须从
`src/tiny_llm/__init__.py` 星号导出，签名与测试期望一致。

## 第二部分：linear

### 2.1 数学公式

仿射变换：矩阵乘 + 偏置。

```
y = x @ w.T + bias
```

- `x`: `(N.., I)`，I 是输入特征数
- `w`: `(O, I)`，O 是输出特征数（每行一个输出单元）
- `bias`: `(O,)`，可选
- `y`: `(N.., O)`

逐元素：`y[..., j] = Σ_i x[..., i] · w[j, i] + bias[j]`——每个输出单元是输入向量的加权和。

**为什么 `w.T`**：w 约定 `(O, I)`（行=输出单元）。`x @ w.T` 让 matmul 的共享中间维 I 对齐，
结果每行是 x 与 w 某行的点积。2D 时 `w.T` 与 `mx.swapaxes(w, -1, -2)` 完全等价（实证 `array_equal=True`）。

### 2.2 addmm 为什么三个参数

`mx.addmm(b, x, w.T)` = `x @ w.T + b`。名字 = add + matrix-matrix product，
融合"两个矩阵相乘（2 个参数）+ 加第三个矩阵（1 个参数）"：

```
mx.addmm( b,  x, w.T ) = (x @ w.T) + b
         ↑    ↑   ↑        ↑       ↑
       被加的 乘号左 乘号右   乘出来  再加它
```

- 参数 1 `b`：被加的（bias，沿最后维广播）
- 参数 2 `x`：乘号左边
- 参数 3 `w.T`：乘号右边

reference 用 `addmm` 而不是 `x @ w.T + b`，因为它是 MLX 的融合 API（一次内核完成乘加，不产生中间张量）。
数值上两者完全等价（实证 `array_equal=True`）。实现 linear 时用哪个都行。

### 2.3 linear 处理的问题

模型内部需要在不同维度空间之间做映射。token 进入模型是 embedding 向量（E 维），
但 attention 需要：Q/K/V 三次投影（E → H×D，可学习，训练出"用什么特征检索/查询/提供内容"），
和一次输出投影（H×D → E，把结果送回 E 维空间供下一层）。

`linear` 是这四个投影的通用实现。注意它是**纯线性**（无激活）——和后面的非线性交替配合才有表达能力。

## 第三部分：多头注意力的切分（核心困惑）

这一部分的讨论主线：从一个注意力头内部发生了什么出发，理解"为什么需要多头"，再理解"为什么嵌入空间按头的数量切分"，最后回答你提出的质疑——切分是不是必然、跨越切分的语义怎么办。

### 3.1 一个注意力头内部发生了什么

先讲**单个**头，因为多头就是多个这样的头并行。一个头要回答的问题：**在输出第 t 个位置时，输入序列里哪些位置值得关注、各贡献多少？**

分四步（这就是你已经写好的 `scaled_dot_product_attention_simple` 的流程）：

**① 投影出三种角色。** 每个位置 i 的输入向量 `x[i]`（D 维）通过三个可学习矩阵，变成三种角色：

```
q[i] = x[i] @ wq    # 查询 query：我想找什么
k[i] = x[i] @ wk    # 索引 key：我有什么可以被找到
v[i] = x[i] @ wv    # 内容 value：被找到后提供什么
```

`wq/wk/wv` 都是 `(D, D)`。同一个 `x[i]` 乘三个不同矩阵得到三种角色——矩阵是可学习的，模型训练出"用什么特征提查询、用什么特征做索引、拿什么做内容"。

**② 算分数矩阵。** 查询位置 t 的 q 和所有位置 s 的 k 做点积：

```
score[t, s] = q[t] · k[s]    # (L, L) 矩阵：位置 t 对位置 s 的关注强度
```

点积大 = 两个向量方向一致 = 语义相近 = 关注度高。

**③ 缩放 + softmax。** 除以 `sqrt(D)` 防止点积随维数膨胀（D 大时点积方差大，softmax 会饱和），然后对每一行做 softmax，归一化成权重（和为 1）。

**④ 加权求和。** `softmax(score/sqrt(D)) @ v`：输出位置 t = 所有位置 v[s] 按权重的加权和。

单头形状流动（用 test_task_1 的 DIM_L=4, DIM_D=5）：

```
x: (4, 5)            4 个位置，每个 5 维
q, k, v: (4, 5)      投影后还是 (4, 5)
q @ k^T: (4, 4)      分数矩阵：位置 t 对位置 s 的关注强度
softmax: (4, 4)      每行归一化成权重
结果 @ v: (4, 5)     每个位置 = 所有位置内容的加权和
```

"对序列内所有位置做加权求和"就是 attention 的本质。`scaled_dot_product_attention_simple` 完整实现了这四步，它的 `(..., L, D)` 里 `...` 是任意 batch 前缀。

### 3.2 为什么需要多个头

单个头只有一种关注模式——一套 `wq/wk/wv` 决定"什么样的语义算相近"，只能捕捉一种类型的关系。

但语言里的关系是多类型的：代词指代、句法依赖、位置邻近、语义对齐……不同关系需要不同的关注模式。一个头硬扛全部，能力不够。

多头的做法：H 个独立的头**并行**，每个头有自己独立的 `wq/wk/wv`，各自演化出不同的关注模式，最后把 H 个头的输出拼起来，供下一层组合使用。

（"各自演化出不同模式"是训练中观察到的现象，不是人为指定的——这一点在 3.8 展开。）

### 3.3 E = H × D：嵌入维怎么被切

**E 从哪来。** E = hidden_size，由 embedding 层的输出维度决定——模型设计者先定一个超参数（如 4096），embedding 层把每个 token 变成这个长度的向量。"一个 token 向量多长"的初始答案就是 embedding 决定的。

**E 在全模型不是恒定的。** 维度变化发生在三个位置：embedding 入口（词表索引 → E 维，词表很大而 E 相对小，把稀疏索引压成稠密向量）、FFN 内部（E → 更大宽度，常见约 4E → E，即你记得的"升维降维"）、输出层（E 维 → 词表）。

而 transformer 层与层之间 E 恒定，机制是**残差连接**：

```
x = x + attention(x)   # 子层 1
x = x + FFN(x)         # 子层 2
```

加法要求两个操作数同维，所以每个子层的输出必须回到 E 才能加回 x。**残差只约束子层的进出口，不约束内部**——FFN 内部可以膨胀到 4E，attention 内部也可以重排，只要最终回到 E。这就回答了"为什么 attention 必须 E 进 E 出"：它是子层，要加残差。

**怎么把 H 个头"塞"进同一个网络。** H 个独立头，各自需要一个 D 维空间做 q/k/v。把嵌入维 E 切成 H 份，每份 D 维，即 `E = H × D`。MHA 测试里 E=27, H=3, D=9。

一个 token 的 27 维向量 reshape 成 `(3, 9)` 后：

```
[0..8]    → 头 0 的 9 维
[9..17]   → 头 1 的 9 维
[18..26]  → 头 2 的 9 维
```

实证：`mx.arange(27).reshape(3, 9)` 每行一个头，第 h 个头 = 向量里 `[h*9 : (h+1)*9]` 这一段。

投影矩阵是同样的结构：`wq` 是 `(E, E) = (27, 27)`，它的输出 27 维被**理解**成"3 个头各 9 维的拼接"。头 0 的 query = 输出前 9 维，头 1 = 中间 9 维，头 2 = 最后 9 维。

**注意 D 的双重含义**：单头场景（Day 1 的 `scaled_dot_product_attention_simple`）里 D 就是向量长度；多头场景里 D 退位成"每头分到的维数"，嵌入维升级为 E = H×D。

### 3.4 拆-算-拼：代码层面的形状流动

**为什么需要手动拆这么多包。**

先看一个底层事实：**matmul 本身就是"最后两维做矩阵乘，前面所有维一律当独立的组"**。

```
mx.matmul((2, 3, 4, 5), (2, 3, 5, 6)) → (2, 3, 4, 6)
# 最后两维 (4,5)×(5,6) 做矩阵乘; 前缀 (2,3) 当批量, 每组独立算自己的矩阵乘
```

**事实：这是整个张量编程的核心范式。**

- matmul 本身就是"最后两维做矩阵乘，前缀当批量"——这是 NumPy 从底层就有的约定。numpy.matmul 的文档明确说：把最后两维当成矩阵，前面的维度当 batch。
- 这不是 attention API 的发明，matmul 就是这个约定。attention 只是继承了这个约定。
- 为什么？因为张量库的基本操作（matmul、softmax over axis、einsum）都工作在这个范式上。这样设计的原因是**组合性**：一个函数写一次，能同时处理 (L,D)、(N,L,D)、(N,H,L,D) 等各种形状，而不需要为每个维度数写一个版本。

1. reshape 不改变数据（不增删、不重排，只是重新解释形状）——它是零成本的元数据操作。
2. 更关键：**"把多个头放在同一个张量里"这个决定本身**，决定了需要 reshape/swapaxes。如果你不用 reshape，你有两个选择：
   a. 用 H 个独立的张量，for 循环逐头算——但那就回到循环，失去向量化（对 MLX 这种 GPU 框架，向量化是性能关键）。
   b. 用嵌套的 list of tensors——那更是把张量编程的优越性丢了。

   所以：**要在"一个张量"里表达"H 个头同时算"，你就必须把头的维度编码进张量的某个轴**。reshape 把 E 拆成 (H,D)，swapaxes 把 H 挪到前缀——这是"在一个张量里并行 H 个头"的必然代价，不是 API 的缺陷。

3. 用户说"多维前面几个就全部都是打包"——是的，这就是 batch 维的语义：前缀维 = "对每个这样的组独立应用同一个操作"。这正是向量化（SIMD/并行）的核心抽象。

**所以"不 solid"的感觉从哪来？**

用户的直觉可能来自：他期望 API 像"显式声明头的维度"那样，比如一个 attention 函数直接接受 (N, H, L, D) 参数并知道 H 是头。但事实上：

- MLX 的 mx.fast.scaled_dot_product_attention 就是这种"显式"API（接受 (N,H,L,D)）！
- 而课程里写的 scaled_dot_product_attention_simple 是更通用的 (..., L, D) 形式，因为它是教学用的，用 matmul 拼出来的。

所以实际上两种 API 都存在：
- 通用型（如 mx.matmul、我们的 simple attention）：前缀当批量，自己管布局。
- 专用型（如 mx.fast.sdp_attention、PyTorch 的 nn.MultiHeadAttention）：显式接受 (N,H,L,D) 或帮你内部做布局管理。

PyTorch 的 nn.MultiHeadAttention 内部就是一堆 reshape/transpose！你去看它的源码，里面就是 q.reshape(B, N, S, D).transpose(1, 2) 之类的操作。也就是说，"手动 reshape/swapaxes"不是课程的特例，是框架内部也在做的事——只是框架帮你包起来了。

**这是不是"为了编写方便"？**

不是。更深层的理由：

1. **组合性/通用性**：一个 (..., L, D) 的 attention 能处理任意维度的前缀——单样本、多 batch、多头、甚至多维 batch。你不需要为每个场景写一个 attention。这是张量编程的核心理念：操作在轴上，形状是数据属性。

2. **内存/性能**：一个连续张量比 list of tensors 内存紧凑、访问高效，GPU 上并行度更高。

3. **布局转换是"数据在算子间流动"的自然语言**：每个算子声明"我在哪些轴上工作"，reshape/swapaxes 就是把数据摆到算子期望的轴上。这就像 Unix 管道里每个命令处理文本流，中间用管道连接——不是 hacky，是模块化的接口协议。


这是整个张量编程的通用范式：**每个操作声明自己作用在哪些轴上，其余轴一律当批量**。`softmax(x, axis=-1)` 只对最后轴归一化，其余轴当批量；`linear` 约定 `w` 是 (输出, 输入)；attention 继承了 matmul 的约定，最后两维是 (L, D)。

这个范式的价值是**组合性**：一个 `(..., L, D)` 的 attention 函数，单样本、多维 batch、多头全都直接可用——H 只是又一个前缀。你的 `scaled_dot_product_attention_simple` 通过了含 `(2, 3, 3)` 多维 batch 的 16 个组合测试，靠的就是这个。如果不这么设计，就要为每个维度数写一个专用函数。

reshape/swapaxes 就是这个范式下的**布局转换器**。要在**一个张量里**同时算 H 个头（而不是 H 个张量 for 循环），头的维度必须编码进某个轴——reshape 把 E 拆成 (H, D)，swapaxes 把 H 摆到前缀批量位置。这些操作不增删数字，只改变数字在轴的排布。

框架内部也这么做：PyTorch 的 `nn.MultiHeadAttention` 源码里就是一堆 reshape + transpose，只是帮你包了一层。

代价：布局错误只有运行时才暴露，没有编译期保护；`swapaxes(-3, -2)` 的轴号写错很常见。这是"形状与语义解耦"的对价——同一个张量可被任意操作以任意方式解读，换来灵活性，失去类型安全。

有没有更"solid"的方案？两种探索：`einsum` 允许显式声明每个轴在运算中的角色（任意重排、收缩、广播），比 matmul 的隐式约定更灵活；给轴命名（PyTorch named tensors、xarray）让布局错误在 API 层就暴露。但它们都没成为主流——命名轴增加了重量，而"无名字的轴 + 约定 + 手动布局"在实践中足够用。所以当前生态的主流仍是隐式约定：这不是没有替代方案，是这个权衡下被广泛选择的一条路。

完整流程（对应 `SimpleMultiHeadAttention.__call__` 要写的七步）：

```
(N, L, E)              query/key/value 输入
   │  linear(query, wq)      ① 投影: E → H*D
(N, L, H*D)
   │  reshape(..., H, D)     ② 拆头
(N, L, H, D)
   │  swapaxes(-3, -2)       ③ 换轴: L 和 H 交换
(N, H, L, D)                  ← 每头成为独立 batch
   │  scaled_dot_product_attention_simple(q, k, v, mask)
   │                          ④ attention: 一次算完所有头
(N, H, L, D)
   │  swapaxes(-3, -2)       ⑤ 换回
(N, L, H, D)
   │  reshape(N, L, H*D)     ⑥ 拼头
(N, L, H*D)
   │  linear(x, wo)          ⑦ 反投影: H*D → E
(N, L, E)             输出
```

**② reshape 拆头**：`(N, L, 27)` → `(N, L, 3, 9)`。最后一个维 27 排成 3 行 9 列，行是头、列是维。不要写死 N，用 `reshape(*shape[:-1], H, D)` 保留任意前缀。

**③ 为什么必须 swapaxes**：matmul 永远在**最后两个维**之间做矩阵乘。看两个候选：

- `(N, L, H, D)`：最后两维 `(H, D)`——matmul 会拿 H 和 D 相乘，而 L 变成前缀，每个位置独立算自己的 `H×D` 乘 `H×D`。这是错的：attention 要的是"每个位置对所有位置"的 `L×L` 注意力。
- 交换 L 和 H → `(N, H, L, D)`：最后两维 `(L, D)`——matmul 正确地算 `L×D 乘 D×L → L×L`，H 变成前缀（和 batch 一样被当"独立的组"）。**每个头自动独立算自己的 L×L 注意力。**

`swapaxes(-3, -2)`：4 维里轴 `-3` 是 L，轴 `-2` 是 H，交换它俩。

**实证：不需要 for 循环。** 换轴后在 `(N, H, L, D)` 上直接调 `scaled_dot_product_attention_simple`（矢量化），和逐头 for 循环的结果**数值一致**。因为 attention 函数支持任意前缀，H 塞进前缀就自动对每个头独立计算。

### 3.5 reference 里的 1

`mx.fast.scaled_dot_product_attention(q=query.reshape(1, -1, DIM_L, DIM_D), ...)`：MLX 内置 API 的输入约定是 `(N, H, L, D)`，第 2 维是 num_heads。测试把 `(B, L, D)` reshape 成 `(1, B, L, D)`：第一个 `1` = **num_heads = 1（单头）**，中间的 `-1` = 把 batch 压成一个维。

为什么是 1：Day 1 的 attention 是单头实现，reference 用 num_heads=1 对照。MHA 把 `(N, H, L, D)` 传进去，H 变前缀，等于对 H 个头各调一次单头 attention——**MHA 复用了 Day 1 的单头实现，没有新写注意力逻辑**。

### 3.6 核心讨论：为什么按头的数量切分嵌入空间

**困惑（你的原话本质）**：把 E 维按 H 切分，每个头只在自己的 D 维子空间里工作，这并不必然——不能保证没有语义需要跨越切分的多个头。单层内这种语义怎么办？

**关键纠正：切分发生在输出空间（分数计算），不在输入（可见性）。**

投影矩阵 `wq` 是**满矩阵**，不是分块对角。数学上展开：

```
q = x @ wq                      # x: (N, L, 27), wq: (27, 27)
头 0 的 query = q[:, :, :9]
            = (x @ wq)[:, :, :9]
            = x @ wq[:, :, :9]  # x 的全部 27 列 × wq 的前 9 列
```

矩阵乘法里，x 的**每一列**都贡献到输出的每一列（只要 `wq` 对应元素非零）。随机 `wq` 几乎处处非零。实证：随机 `wq` 里每个输入维对每个头的输出维都有非零贡献（抽查输入维 0/5/20/26 对三个头都是 9/9）。

由此推出两个事实：

- **头 0 不是"只看 x 的前 9 维"。** 它看到全部输入，只是把 27 维压缩进自己的 9 维输出空间。
- **"跨越原始维度的语义组合"（维度 3 和维度 20 协同）在投影层就解决了**——每个头内部的 9 维输出可以是任何输入维的线性组合。切分没有限制"一个头能表达什么输入模式"。

### 3.7 投影是降维：为什么子空间压缩是多头的机制

3.6 说头 0"把全部输入压缩进自己的 9 维输出空间"——这个压缩在数学上是什么？

**投影是线性降维。** 头 h 的 query 是：

```
q_h = x @ wq[:, h*D:(h+1)*D]    # (…, E) @ (E, D) → (…, D)
```

E=27 的输入经过 (27, 9) 的矩阵，得到 9 维输出。27 个自由度压缩成 9 个自由度——只要投影矩阵列满秩，q_h 的取值就落在 27 维空间里的一个 9 维子空间里，所以叫"投影到子空间"。

**降维是多头特有的。** 单头场景（Day 1 的 `scaled_dot_product_attention_simple`）里 D 就是向量长度，wq 是 (D, D)，输入输出同维，没有压缩。降维之所以出现，是因为多头里每头只分到 D = E/H < E 的输出空间（3.3 讲过，E = H×D 意味着每头只有总预算的 1/H）。

**为什么这个降维是设计意图，不是缺陷。** 关键：**降维正是多头分化的机制本身。**

每个头被迫把 E 维信息压进自己的 D 维输出。但不同头的投影方向不同（wq 不同列段张成的空间不同），于是：

- 头 0 保留与它投影方向相关的信息，丢弃其余；
- 头 1 用另一组方向，保留另一部分信息；
- 各头保留各自不同的 D 个自由度。

如果每头都全维处理（不降维），多头就退化成 H 份完全相同的注意力——所有头看到同样的信息、算同样的分数，分化无从谈起。**正是"每头只能保留 D 维分量"这个约束，迫使不同头从不同角度分析输入**。压缩不是无奈，是让头与头之间产生区分度的机制。

直观类比：让三个分析师各自只能写一页摘要（每页 9 行），但每个分析师的摘要模板（投影方向）不同——一个抓句法、一个抓指代、一个抓位置。他们被迫把全部信息压缩进各自的 9 行，合起来才是全面分析。

**整体形状没变，降维在"每头解释"层面。** 整体看，`linear(query, wq)` 是 (…, E) @ (E, E) → (…, E)，形状保持——残差流的约束（3.3）。降维只发生在"把 E 解释成 H 个 D"之后：整体是 E→E 的变换，内部由 H 个并行的 E→D 降维投影组成。

所以准确说法：**多头 = 整体形状保持的 E→E 变换，内部由 H 个并行的"降维到子空间再算注意力"组成，最后 wo 把 H 段重组回 E**。

收束成一条线：**投影（每头 E→D 降维压缩）→ 子空间里算分数 → 拼接 → wo 重组回 E（残差流）**。降维在这里的角色是让每个头被迫从不同角度压缩信息、从而分化——它不是信息丢失的缺陷，是"多头"这个词的含义本身。

### 3.8 真实的约束，以及为什么这个约束可以接受

切分真正约束的是**注意力分数的计算**：头 0 的分数 = 头 0 的 q 和头 0 的 k 在头 0 的 9 维空间做点积，头 0 的 query 永远碰不到头 1 的 key。**跨头的分数交互在单层内确实不存在——你的质疑在这里成立。**

为什么这个约束可以接受，三个理由：

**1. 头是训练中自己分化的，不是人为切的语义。** 每个头有独立的 `w_q/w_k/w_v` 行，训练时各自演化出"关注什么"。某个语义模式横跨两个头时，它不被禁止，而是被**某个头**在投影层学会了表达（因为每头都能看到全维输入）。切分限制的是"一个头的分数不能和另一个头的分数同层交互"，不是"一个头能表达什么输入模式"。

**2. 跨头语义推迟到下一层解决。** 3 个头的输出拼接回 27 维，下一层的投影（又是满矩阵）**任意组合跨头的特征**：

```
拼接: [out_0 | out_1 | out_2]     # 27 维
下一层: concat @ wq'              # wq' 满矩阵, 可自由混合 3 个头的信息
```

这是深度网络的**局部性设计**——单层内约束、层间自由组合，和 CNN"单层局部感受野、深层全局"是同一个结构。

**3. 计算效率。** 每个头在 D=9 的低维空间算注意力，投影矩阵小、可并行。如果单层内允许头间自由交互，要么破坏切分结构，要么付出额外的通信/计算代价。

### 3.9 学术诚实：切分不是必然

确实有研究探索跨头交互（交错/共享 query 空间的变体、头合并与剪枝等方向）。标准 MHA 的"先切分、后独立"**不是数学必然，是一个工程取舍**：用"单层内分数不跨头"换"实现简单 + 可并行 + 层间可重组"，而实践中这个取舍被证明足够有效。

所以你的判断是对的：它不是唯一的解法，也不是逻辑上被迫的选择，而是 Transformer 选定的一条路——理解这一点，比记住"E = H×D"这个公式更重要。
