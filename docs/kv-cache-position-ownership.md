# 位置与槽位: KV cache 里一个整数的两个语义

decode 每一步都要回答两个问题：

1. 这个 token 在序列里排第几。答案决定 RoPE 把它旋转多少度。
2. 这个 K/V 写到数组的第几个格子。答案决定存储地址。

在 dense 缓存、单请求、连续追加的情形下，两个答案总是同一个数。于是代码里只保留了一个整数，两种语义共用它。这个共用是后续所有麻烦的来源。

代码里对应两处。`src/tiny_llm/kv_cache.py:113` 的 `update_and_fetch` 用 `self.offset` 决定写入槽位；`src/tiny_llm/qwen3_week2.py:190` 的模型入口把同一个数作为参数传给 RoPE，并在 `cache[0].offset != offset` 时抛错。测试 `tests_refsol/test_week_2_day_1.py::test_task_3_rejects_a_position_that_disagrees_with_the_cache` 覆盖后一处。

## 前情: 一个 offset 被三处消费

Week 2 的接口里，同一个整数被三个地方读：

| 消费者 | 拿它做什么 | 真正需要的东西 |
|---|---|---|
| RoPE | 切 cos/sin 表，取 `[offset, offset+L)` 行 | position：这一步的 token 排第几 |
| cache 写入 | 决定切片起点 `[offset : offset+S]` | slot：这个 K/V 写到第几个格子 |
| 掩码 | 由 `S = offset + L` 定列数 | 总长度 S：query 能看到多少列 |

三种语义不同，值却相等。原因是 dense、连续、单请求三条前提同时成立，把它们压到了同一个数上。

## 这个设计值得推敲的地方

**没有一处能验证自己拿到的是对的。** RoPE 收到 5，它无法知道 slot 是不是 5；cache 收到 slot 5，也无法知道 position 是不是 5。一致性只存在于调用方的脑子里。

**错误是静默的。** 三处用了不同的值，形状依然合法，dtype 依然对，只是数值错。所以测试要专门造一条来抓它：`test_task_3_rejects_a_position_that_disagrees_with_the_cache` 传 `offset=1` 给空 cache，要求抛 `ValueError`。

**守卫只能放在模型的入口。** 它检查的是跨模块的约定，不属于任何单个模块的内部不变量。cache 不知道 RoPE 用了什么，RoPE 也不知道 cache 用了什么，只有同时持有两者的人能发现它们不一致。

一个更好的组织方式是让每处只拿自己的语义：RoPE 拿 positions，cache 拿 slots，掩码从 slots 派生 S。这样没有跨模块的对齐要求，因为每处的输入就是它要用的东西。

代价转移到调用方：它要同时算出 positions 和 slots。错点没有消失，从「两个变量是否相等」变成了「同一个表达式写了两遍、有没有写岔」。只有让 positions 和 slots 指向同一个数组，才算真正消除。这就是设计 C。

## 状态归谁

模型本身没有状态。同一份权重、同一个输入张量，`__call__` 的输出相同，与调用历史无关。所有「记住」的东西必须放在模型之外。这是推理引擎能并行服务多个请求的前提：模型内部一旦有跨调用的状态，两个请求就无法共用同一份权重。

状态分布在三层：

| 层 | 持有什么 | 生命周期 | 共享范围 |
|---|---|---|---|
| 推理引擎 | 请求队列、batch 组成、调度顺序 | 进程 | 全部请求 |
| 请求 | position、已生成 token、采样参数、终止条件 | 从创建到结束 | 单请求 |
| KV cache | 历史 token 算出的 K/V、slot 计数 | 跟随请求；前缀缓存时跨请求 | 单请求或共享前缀 |

**位置的权威在请求这一层。** 请求知道自己是第几步、下一步该填哪个位置、要不要撤销。引擎知道哪个请求该跑。cache 只知道「我这里存了几个 K/V」，它不知道这些 K/V 属于序列里的哪些位置——在连续追加时两者恰好相等，在跳号或共享前缀时不等。

### 所有权与解释权会分开

前缀缓存是两者分离的实例。多个请求共享同一段前缀的 K/V，物理存储只有一份，所有权归缓存；但「这段前缀在各自序列里占第几位」的解释权归每个请求。同一个槽位，在请求 A 里是位置 3，在请求 B 里可能是位置 0。

这种分离要求接口能把「存什么」和「存在哪」分开传。现在的 `update_and_fetch(k, v)` 做不到，它只能按自己的计数推断地址，所以共享前缀必须靠复制或者更底层的页表来绕。

### cache 自己的状态机

去掉跨请求的部分，单个 dense cache 的状态只有三个量：`key_values` 是否为 `None`、`offset`、`capacity`。

```
空        key_values is None, offset = 0
  ↓ update(L)                      分配或直接存, offset = L
部分填充  0 < offset < capacity
  ↓ update(L)                      写入 [offset, offset+L), offset += L
满        offset == capacity
  ↓ rewind(n)                      offset -= n
部分填充
  ↓ reset                          offset = 0
空        capacity 模式下保留数组，无 capacity 模式下释放
```

两条约束贯穿所有转移：

- `offset` 永远等于有效数据的长度，返回值永远只暴露 `[:offset]`。
- 物理数组的长度在 capacity 模式下恒为 `capacity`，与 `offset` 无关；无 capacity 模式下恒等于 `offset`。

超出容量的 `update` 是一次被拒绝的转移：抛错，状态不变。测试 `test_capacity_rewind_and_overflow_preserve_the_logical_prefix` 在抛错后断言 `offset == 3`，检查的就是这一点。

### 分层决定了接口形状

模型无状态，所以位置只能由调用方传入，不能从模型里读。

请求持有位置，所以 `offset` 是请求的属性，不是缓存的属性。

缓存在连续追加时能自己推断 slot，所以接口里省掉了地址参数——这个省略只在三条前提同时成立时有效。

前缀缓存需要把所有权和解释权分开，所以地址必须变成显式参数。这是设计 C 的动机，也是分页缓存存在的理由。

## 为什么两个答案默认相同

dense 缓存的定义就是「逻辑位置等于物理下标」。第 j 个 token 的 K/V 存在第 j 个槽位上，不重排、不跳跃。`update_and_fetch` 收到的参数只有 `(key, value)`，它没有地址可依据，只能用自己记的「已经存了多少」当作「下一个该写哪里」。这个数既是已存长度，也恰好是下一个 token 的位置。

RoPE 那边拿到的是调用方传入的 `offset`，它切 cos/sin 表的第 `offset` 到 `offset+L-1` 行。此刻还没有写缓存，所以它只能用参数，不能用 `cache.offset`。

两个数来自两个地方，值是相等的。守卫检查的就是这个相等。

## 相等的前提在哪些情形下破裂

四个：

**批处理。** 一个 batch 里三个请求的历史长度分别是 5、2、0，这一步送入的位置就是 5、2、0。模型层收到一个 `(3, L, E)` 的张量，但位置不是一个标量。`cache` 列表里每个元素有自己的「已存长度」，模型只有一个参数。

**前缀缓存。** 多个请求共享同一段前缀的 K/V，各自的逻辑位置不同。位置由请求决定，存储里只有一份 K/V。

**投机解码。** 先写入 3 个草稿 token，验证后只有 1 个被接受，另外 2 个要 `rewind`。位置前进了 3，缓存退回 1，两者在撤销的那一刻不一致。

**跳号验证。** 只补第 7 个位置，缓存里已经有 5 个。位置是 7，槽位是 5。

前两种是「多个请求，一个模型参数」；后两种是「位置与已存长度解耦」。

## 缓存为什么要自己推断地址

接口里没有地址。`update_and_fetch(key, value)` 能做的事只有按顺序追加。它假设「调用方永远按顺序送、永远不跳号、永远不退」。这个假设在单请求连续生成时成立，在其余四种情形下不成立。

把地址也交给调用方，缓存就不再需要这个假设。它变成纯粹的存储：你给我哪些格子、写什么，我就写。

旋转仍然发生在调用方，在数据进入缓存之前。缓存不知道 K 被旋转过，也不需要知道。它只处理数值和地址。

## 三种写法的差别

**A. 拆成 prefill 与 decode 两个入口。**

```
prefill(inputs, cache)      位置恒从 0 开始
decode(token, cache)        位置 = cache[0].offset
```

位置从缓存派生，参数消失。代价是只覆盖连续追加；前缀缓存的 prefill 不从 0 开始，batch 的 decode 又需要每请求位置。

**B. 位置与 token 绑定，作为输入。**

```
__call__(inputs, positions, cache)
# inputs     (B, L)  token id
# positions  (B, L)  每个 token 的绝对位置
```

`offset` 这个标量消失，位置成为数据。batch 自然支持，位置可以跳。但缓存内部仍持有自己的槽位计数，两者仍可能不一致，守卫仍然需要。

**C. 把槽位也交给缓存。**

```
q = rope(q, positions)
k = rope(k, positions)
k, v, offset, mask = cache.update_and_fetch(k, v, slots=positions)
```

缓存不再持有私有的槽位计数。它按 `slots` 写，写完之后的已存长度由 `slots` 派生。位置只有一个数组，RoPE 和缓存各取其中一份语义：前者取角度，后者取地址。两者不可能偏离，因为它们没有各自的副本。

严格说，C 传给 RoPE 的 `positions` 和传给缓存的 `slots` 可以写成两个变量。只要它们由同一个表达式算出，就不存在独立状态。现在的实现里，`cache.offset` 是独立状态，所以需要检查。

## dense 的边界

`slots = [0, 2, 4]` 能写进 dense 数组，因为每个下标都合法。问题出在读：`_logical_key_values`（`src/tiny_llm/kv_cache.py:102`）按 `[:offset]` 切前缀，切出来的是 `[0, 1, 2, 3, 4]`，其中 1 和 3 是分配时的零，不是真实的 K/V。注意力会把这些零当成历史。

dense 缓存因此要求 `slots` 连续、从零开始、无空洞。空洞要靠分页缓存：物理页可以散落在任意位置，页表负责把逻辑位置映射到物理页，页内仍然连续。这是 Week 3 之后的实现接续点。

## 现在这个接口的取舍

课程保留了标量 `offset`，同时覆盖单请求与批处理（签名是 `int | list[int] | mx.array`），代价是多了一个可以传错的参数和一道入口守卫。守卫的存在本身说明这个可错点在类型上没有消除。

更彻底的做法是 C。它要求 dense 缓存接受 `slots`，也要求调用方算出与 `positions` 一致的地址。在单请求场景下这多此一举，在批处理与分页场景下是必需的。
