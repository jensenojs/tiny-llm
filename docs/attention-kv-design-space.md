# 注意力的键值存放: MHA、GQA、MQA、MLA 的比较

> 自回归生成的 decode 阶段, 每产生一个 token, 注意力层都要把此前全部位置的键 (key) 与值 (value) 从内存读一遍. 随着上下文增长, 由上下文生成的 KV Cache 大小及其单步读取量，会超过模型权重本身, 成为每一步的主要开销; 它们占的内存也决定了一台机器能同时容纳多长的上下文. MHA、GQA、MQA、MLA 是缩小这部分存储的四种做法. 四者都受同一条形状约束: 每个头的查询 (query) 与键必须等宽, 因为两者要做点积. 四者也都要和模型效果相权衡. MLA 改变了存放的内容, 又带出第二条约束. 本篇从读取量出发, 先找出能改的因子, 再依次看减少份数 (MHA → GQA → MQA) 与改变存放物 (MLA) 两条路各自换来什么、付出什么, 最后标出四者的等价处与断裂处.
>
> 数字以 Qwen3-0.6B (GQA) 和 DeepSeek-V2 (MLA) 为例. 代码块各自独立, 只依赖 Python 与 mlx, 可以保存成文件运行, 也可以整块贴进交互式解释器; 每块下方的 text 块是实际输出, 运行环境为 mlx 0.32.0、Python 3.10.18、arm64. 文献中的结论都对照原文核对过, 出处列在末尾.

## decode 每一步都要重读全部历史

注意力层为每个位置 t 算出三个向量: 查询 q_t、键 k_t 与值 v_t. 位置 t 的输出是历史上各位置的值的加权和, 权重由 q_t 与每个 k_j 的点积经过 softmax 得到:

```text
score_{t,j} = q_t · k_j                 j = 0, 1, …, t   (实现中还要除以一个与宽度有关的常数)
w_{t,j}     = softmax_j(score_{t,j})    对 j 归一化, 权重和为 1
out_t       = Σ_j w_{t,j} · v_j
```

decode 每次只新增一个位置. 因果掩码使位置 j 的计算只用到 j 及其之前的输入, 后来的 token 不会改变 k_j 与 v_j, 所以它们算出一次就可以存下来. 这份存储叫 KV cache, 每一层各有一份. 第 t 步只需为新位置算 q_t、k_t、v_t, 但打分和加权求和要用到全部 t+1 个 k 与 v, 于是每一步都要把整份 cache 从内存读进计算单元.

Qwen3-0.6B 每层为每个位置存 1024 个数的 k 和 1024 个数的 v (1024 这个宽度由哪些因子组成, 在「读取量由哪几个因子相乘」一节拆开), 共 28 层, 以 bf16 存放, 每个数 2 字节. 下面的脚本算出 cache 的大小, 并和每一步同样要读一遍的权重对比:

```python
kv_width = 1024                    # Qwen3-0.6B 每层每个位置的 k 宽度, v 同宽
layers = 28
nbytes = 2                         # bf16
weights = 596.0e6                  # 全部参数个数, 含与出口共用的嵌入表

per_layer = 2 * kv_width * nbytes  # k 与 v 各一份
per_token = per_layer * layers
print(f"每 token 每层   2 × {kv_width} × {nbytes} B = {per_layer} B = {per_layer // 1024} KiB")
print(f"每 token 28 层  {per_token} B = {per_token // 1024} KiB")
for S in (2048, 32768):
    print(f"S = {S:>5}       每步读 cache {per_token * S / 2**30:.2f} GiB")

print(f"每步读权重 bf16        {weights * 2 / 1e9:.2f} GB, 与 cache 相等时 S = {weights * 2 / per_token:,.0f}")
print(f"每步读权重 4 bit 打包  {weights * 0.5 / 1e9:.2f} GB, 与 cache 相等时 S = {weights * 0.5 / per_token:,.0f}")
```

```text
每 token 每层   2 × 1024 × 2 B = 4096 B = 4 KiB
每 token 28 层  114688 B = 112 KiB
S =  2048       每步读 cache 0.22 GiB
S = 32768       每步读 cache 3.50 GiB
每步读权重 bf16        1.19 GB, 与 cache 相等时 S = 10,393
每步读权重 4 bit 打包  0.30 GB, 与 cache 相等时 S = 2,598
```

每一步读的权重量是固定的, 读的 cache 量随历史长度 S 线性增长. 权重以 bf16 存放时, 两者在 S ≈ 10,393 处相等; 权重保持 4 bit 打包 (不计 scales 与 biases) 时, 交点提前到 S ≈ 2,598. 越过交点之后, 每一步的读取以 cache 为主.

```text
每步读的字节
  │                                   ╱ cache: 112 KiB × S
  │                                 ╱
  │ ──────────────────────────────╳──────────── 权重 1.19 GB (bf16)
  │                             ╱ S ≈ 10,393
  │                          ╱
  │                       ╱
  └──────────────────────────────────────────── S
```

多个请求同时 decode 时, 权重读一次就供全部请求使用, cache 则每个请求各有一份, 交点按请求数成比例提前. decode 通常受内存带宽限制, 在这个前提下, 长上下文与批量服务两种场景里, 缩小 cache 都直接减少每一步要读的字节, 也增加一台机器能同时容纳的上下文总长.

## 读取量由哪几个因子相乘

前面算出的每层 1024 个数由两个因子组成. Qwen3 的注意力把查询分成 H 个头, 每个头宽 D; 键与值分成 G 组, 每组宽 D; 1024 = G × D = 8 × 128. 四个记号各对应模型配置文件 config.json 里的一个字段:

```text
记号  config.json 字段        Qwen3-0.6B   含义
E     hidden_size             1024         层与层之间传递的向量宽度, 注意力的输入与输出都是这个宽度
H     num_attention_heads     16           查询头的个数
G     num_key_value_heads     8            键值组的个数, 每组一份 k 与一份 v
D     head_dim                128          每个头 (每组) 的宽度
```

一层注意力里各个量的形状由这四个数决定. 下图中 L 是这一步新送入的位置数, S 是连同历史在内的总位置数:

```text
x (L, E)
 ├─ W_q ─→ (L, H·D) = (L, 2048) ─ 切成 16 段, 每段 128 ──────────────┐
 ├─ W_k ─→ (L, G·D) = (L, 1024) ─ 切成 8 段 ─→ 追加进 cache ──┐      │  第 h 个查询头
 └─ W_v ─→ (L, G·D) = (L, 1024) ─ 切成 8 段 ─→ 追加进 cache ──┴──────┴→ 读第 h // (H/G) 组
                                                                         打分 (H, L, S) → 加权 (H, L, D)
                                                                         → 拼回 (L, H·D) ─ W_o ─→ (L, E)
```

D 必须直接从配置读取. 若按 E / H 推算, 得到 64, 只有实际值的一半, 后面所有关于 cache 的数字都会少算一半. Qwen3-0.6B 的 H·D = 2048, 比 E 宽一倍, 头宽是单独设定的超参数, 不由 E 与 H 决定; 查询与键的归一化层 (q_norm、k_norm) 和旋转位置编码的宽度都是 128, 可以用来核对.

每一步读取的 cache 字节数于是写成六个因子之积 (这里假定 v 与 k 同宽, Qwen3 正是如此; 「能改什么」一节说明这一点并非必需):

```text
每步读的 cache 字节 = 2 × G × D × b × N × S
                     │   └─┬─┘   │   │   └─ 历史长度: 滑动窗口、线性注意力改变的是它
                     │     │     │   └───── 层数: 由模型规模决定
                     │     │     └───────── 每个数的字节数: KV 量化改变的是它
                     │     └─────────────── 组数 G 与组宽 D: 本篇讨论的对象 (MLA 把 2·G·D 整体换成另一个宽度)
                     └───────────────────── k 与 v 各一份
```

b、N、S 三项各有专门的方法. 本篇只讨论 2·G·D 这一项, 也就是每层为每个位置存多少个数; 后文会看到, 这一项的各种改法最终都落在「cache 里存什么」上, 而另外两项也可以从同一个角度提问: 每个数存几位, 是在不改变存放物的前提下压缩它的表示; 历史长度 S 能否不让 cache 随它增长, 是把「与头数无关」换成「与长度无关」.

## 能改什么: 一条形状约束与效果的代价

要缩小 2·G·D, 先要分清哪些地方受硬约束, 哪些地方只是取舍.

形状上的硬约束来自打分. 打分是 q 与 k 的点积, 两个向量逐位相乘再求和, 所以每个查询头与它所读的那组键必须等宽. 值只参与加权求和, 权重是打分经过 softmax 得到的标量, 个数等于历史位置数 S, 与值的宽度无关. 下面的例子让 q 与 k 宽 8, v 宽 5, 再把 k 换成宽 6:

```python
import mlx.core as mx

mx.random.seed(0)
L, S = 3, 4                       # 3 个 query 位置, 4 个历史位置
q = mx.random.normal((L, 8))      # q 与 k 同宽 8
k = mx.random.normal((S, 8))
v = mx.random.normal((S, 5))      # v 宽 5, 与 q、k 不同

w = mx.softmax(q @ k.T / 8**0.5, axis=-1)
out = w @ v
print("权重", w.shape, "每行和", [round(x, 6) for x in w.sum(axis=-1).tolist()])
print("输出", out.shape)

k_bad = mx.random.normal((S, 6))  # k 宽 6, 与 q 不同
try:
    q @ k_bad.T
except ValueError as e:
    print("q 宽 8, k 宽 6:", e)
```

```text
权重 (3, 4) 每行和 [1.0, 1.0, 1.0]
输出 (3, 5)
q 宽 8, k 宽 6: [matmul] Last dimension of first input with shape (3,8) must match second to last dimension of second input with shape (6,4).
```

v 的宽度与 q、k 不同时, 注意力照常计算, 输出随之变为 5 维; k 与 q 不等宽时, 打分无法计算. 多数模型让 v 与 k 同宽, 这是实现上的方便, k 与 v 可以共用同一套切分和存放逻辑. 后文的 DeepSeek-V2 就是一个例外: 每个头的键宽 128 + 64 = 192, 值宽 128.

这条约束限定了缩小 G·D 的方式. 只缩小键一侧的 D 不可行, 要缩就得连同查询一起缩, 每个头用来打分的向量随之变短. 能在键值一侧单独调整的只剩组数 G.

效果上的代价来自头与头之间的分工. 设置多个查询头, 是为了让每个头用自己的 k 打分、读自己的 v, 在同一段历史里关注不同的位置、取回不同的内容. G 小于 H 时, 同一组的头共用一份 k 与 v, 彼此只能靠各自的 q 区分; G 越小, 共用一份的头越多.

四种形态面对的是同一个取舍: 在每头 q、k 等宽的约束下, 用多少存储换多少头的独立性. 显存与带宽的压力推动 G·D 变小, 效果要求每个头尽量保有自己的 k 与 v. 后面两种解法, 一种减少份数, 另一种改变存放的内容.

## 减少份数: MHA → GQA → MQA

组数 G 是键值一侧唯一能单独调整的因子. 从 G = H 一路减到 G = 1, 得到三种形态 (查询头数 H = 16, 每头宽 D = 128):


| 架构 | 查询头（Query 分组） | 共享映射 | 实际缓存的 Key/Value | 份数 | 单 token 单层显存 (bf16) |
| --- | --- | --- | --- | --- | --- |
| **MHA** | `q0`, `q1`, `q2`, `q3` ... `q15` | 1 对 1 | `k0v0`, `k1v1`, `k2v2`, `k3v3` ... `k15v15` | 16 份 | 8 KiB |
| **GQA** | `[q0, q1]`, `[q2, q3]` ... `[q14, q15]` | 2 对 1 | `k0v0`, `k1v1` ... `k7v7` | 8 份 | 4 KiB |
| **MQA** | `[q0, q1, q2, q3 ... q15]` | 16 对 1 | `k0v0` | 1 份 | 0.5 KiB |


MHA (multi-head attention, Vaswani 等 2017) 中每个查询头有自己的一份 k、v. MQA (multi-query attention) 让全部查询头共用一份. GQA (grouped-query attention) 介于两者之间, 把查询头分成 G 组, 组内共用一份. Qwen3-0.6B 取 G = 8, 每两个查询头共用一组.

GQA 的计算与 MHA 形式相同. 把每组 k、v 复制给它服务的每个头, 得到一份 MHA 形状的 k、v, 再按 MHA 计算, 结果与 GQA 逐元素一致:

```python
import mlx.core as mx

mx.random.seed(0)
H, G, D, S = 4, 2, 8, 5
q = mx.random.normal((H, D))              # 一个 query 位置, 4 个头
k = mx.random.normal((G, S, D))           # cache 里只有 2 组
v = mx.random.normal((G, S, D))

# GQA 的写法: 第 h 个头读第 h // (H/G) 组
out_gqa = mx.stack([
    mx.softmax(k[h // (H // G)] @ q[h] / D**0.5) @ v[h // (H // G)]
    for h in range(H)
])
# 把每组复制给它服务的头, 得到一份 MHA 形状的 k/v, 再按 MHA 计算
k_rep = mx.repeat(k, H // G, axis=0)      # (H, S, D)
v_rep = mx.repeat(v, H // G, axis=0)
out_mha = mx.stack([mx.softmax(k_rep[h] @ q[h] / D**0.5) @ v_rep[h] for h in range(H)])
print("GQA vs 复制后的 MHA  最大差", float(mx.abs(out_gqa - out_mha).max()))
print("cache 里的 k:", k.shape, " 复制后:", k_rep.shape)
```

```text
GQA vs 复制后的 MHA  最大差 0.0
cache 里的 k: (2, 5, 8)  复制后: (4, 5, 8)
```

GQA 因此可以看成一个受约束的 MHA: 同组各头的 k、v 被强制取相同的值. cache 只存未复制的 G 份, 复制在读取时完成; tiny-llm 的 scaled_dot_product_attention_grouped 用 reshape 加广播实现这一步, 复制品不写进内存.

约束越强, 效果损失越大, 不同文献报告的损失量级不一致. Shazeer 2019 提出 MQA, 报告解码明显加快, 质量只有轻微下降. Ainslie 等 2023 指出 MQA 会造成质量下降, 并提出 GQA: 用原预训练 5% 的计算量从 MHA checkpoint 继续训练, GQA 的质量接近 MHA, 速度接近 MQA. DeepSeek-V2 技术报告附录 D.1 在 7B dense 模型上做了对照, 三个模型都训练 1.33T token, 通过调整层数把参数量对齐到约 7B (MQA 7.1B, 另外两个 6.9B):

```text
基准 (指标)        MQA    GQA (8 组)   MHA
BBH (EM, 3-shot)   33.2   35.6         37.0
MMLU (5-shot)      37.9   41.2         45.2
C-Eval (5-shot)    30.0   37.7         42.9
CMMLU (5-shot)     34.6   38.4         43.5
```

在这组较难的基准上, 四项分数都按 MHA、GQA、MQA 的顺序递减. G 减到 1 之后, 这条路已经到底.

## 改变存放物: MLA

MQA 将键值的份数压缩至 1 份，沿着削减份数的分支已无压缩空间。

如果还想继续降低解码时的 KV Cache 显存占用与内存带宽开销，同时又不希望所有注意力头强制退化为完全相同的视野，就只能改变缓存里实际存放的物理实体。MLA（Multi-Head Latent Attention）的核心做法是：在显存中不再保存任何特定头已经成型的真实 Key 与 Value，而是引入一个低维的公共压缩隐向量；显存只存这一份压缩包，运算时再进行映射。  

> 以下推导采用工程实现与显存排布的**行向量体系**（即单 token 向量在左、投影权重矩阵在右，乘法形式一律为 $x W$）。

### MLA 的计算流程与数据流

以 DeepSeek-V2 的实际规格为例：输入隐藏维度 $E = 5120$，查询头数 $H = 128$，每个头的特征维度 $D = 128$。   

在标准 MHA 中，单步生成一个 token，模型必须为 128 个头分别计算并存入 Key 和 Value，写进显存的是一张二维表，单位置单层就要占用 $128 \times 128 \times 2 = 32,768$ 个浮点数。   

MLA 将整个数据流划分为两个阶段：

#### 写入阶段：未分头的低维压缩写入

当前位置的输入向量 $x$ 形状为 $(1 \times 5120)$。它首先右乘一张所有头共享的下投影矩阵 $W_{\text{down}}$（形状 $5120 \times 512$），直接压成一排 512 个数，记为压缩向量 $c$：   


```
1 个 token 的输入 x        下投影权重矩阵 W_down        存进显存的压缩向量 c
   (1 × 5120)          ×      (5120 × 512)        =       (1 × 512)
[ 5120 个数的一排 ]                                    [ 512 个数的一排 ]
```

代数表达式为：$c = x W_{\text{down}}$

- $W_{\text{down}}$ 是一张固定的模型参数矩阵，形状为 $(E \times d_c) = (5120 \times 512)$。 
- 实际追加写进 KV Cache 的，只有这单行 512 个浮点数，完全剥离了“128 个头”这一维度。
- 当自回归生成积累了 $S$ 个历史位置后，Cache 在显存中表现为矩阵 $C$，形状为 $(S \times 512)$。

#### 读取阶段：各头的定义与历史还原的算力陷阱

在数学形式上，第 $h$ 个头专属的键 $k_h$ 和值 $v_h$（形状均为 $1 \times 128$），由各自专属的上投影解压矩阵 $U_h$（形状 $512 \times 128$）和 $V_h$（形状 $512 \times 128$）映射得到：   

$$k_h = c U_h, \qquad v_h = c V_h$$


因为 128 个头各自的解压矩阵 $U_0, U_1, \dots, U_{127}$ 参数各不相同，同一个 $c$ 还原出来的 128 个键彼此互不相同，各个头保留了各自独立的打分视野。   

但在自回归 decode 阶段，这引出了严重的计算负担： 当前步只有一个新 token 的查询行向量 $q_h$（形状 $1 \times 128$），而历史已经累积了 $S$ 个位置（例如 $S = 32,768$）。如果按照直觉，先将显存中 $S \times 512$ 的矩阵 $C$ 还原成该头的历史键矩阵 $K_h = C U_h$（形状 $S \times 128$），再执行打分 $\text{score}_h = q_h K_h^\top$：   

每生成一个 token，模型都要额外对历史的所有 $S$ 个位置计算一次大矩阵乘法，显存里还必须物化出一个随 $S$ 线性膨胀的中间矩阵 $K_h$。在长序列场景下，这种开销让计算单元难以承担。   

### 矩阵吸收：结合律如何免去对全部历史的计算

MLA 在 decode 阶段完全避免了上述对历史矩阵 $C$ 的投影计算，其依据是矩阵乘法的**结合律**。   

#### 打分重排（Key 侧吸收）

按原本逻辑，打分是当前行向量 $q_h$ 与历史键矩阵的转置相乘：   

$$\text{score}_h = q_h K_h^\top = q_h (C U_h)^\top$$

根据转置性质 $(C U_h)^\top = U_h^\top C^\top$，代入后利用结合律重排括号：

$$\text{score}_h = q_h (U_h^\top C^\top) = (q_h U_h^\top) C^\top = \tilde{q}_h C^\top$$

   其中：

- $\tilde{q}_h = q_h U_h^\top$ 是变换后的新查询向量。   
- 它的形状为 $(1 \times 128) \times (128 \times 512) = (1 \times 512)$。   

两种运算路径的张量形状与内存行为对比如下：

```
路径 A：不使用结合律 (显式还原历史序列，计算随 S 崩溃)
  历史 Cache C          解压矩阵 U_h           解压后的历史键矩阵 K_h          当前查询转置 q_h^T       打分转置
   (S × 512)      ×     (512 × 128)     =        (S × 128)          ×    (128 × 1)     =     (S × 1)
 [S 行 512 列]        [固定权重矩阵]           [S 行 128 列的中间矩阵]         [128 个数的一排]       [S 个分数]
                                         ▲
                                         │ 随着历史 S 增长，产生一个与 S 成正比的中间矩阵，
                                         └ 必须全部算出来并写进显存再读出


路径 B：使用结合律 (矩阵吸收: 括号改到查询一侧，与 S 完全脱钩)
  当前查询 q_h          解压矩阵转置 U_h^T      吸收后的新查询 q̃_h            历史 Cache 转置 C^T     打分向量
   (1 × 128)      ×     (128 × 512)     =        (1 × 512)          ×    (512 × S)     =     (1 × S)
 [128 个数的一排]     [固定权重矩阵]           [512 个数的一排]               [512 行 S 列]          [S 个分数]
                                         ▲
                                         │ 只对当前 1 个 token 变换，宽度固定为 512，
                                         └ 中间结果仅 512 个数，直接留在寄存器中，尺寸与 S 完全无关
```

在路径 B 中，$U_h^\top$ 直接被“吸收”进了当前步的查询向量 $q_h$ 中。因为只涉及当前这一个 token，生成 $\tilde{q}_h$ 的浮点运算量微乎其微，中间结果常驻在片上高速寄存器内。历史 Cache 矩阵 $C$ 维持 $S \times 512$ 的低维状态，在打分阶段直接与 $\tilde{q}_h$ 执行单次 GEMV，显存中从未生成过任何历史位置的 128 维键 $K_h$。

#### 加权聚合重排（Value 侧吸收）

得到注意力权重行向量 $w_h$（形状 $1 \times S$）后，对历史值向量进行加权求和：

$$\text{out}_h = w_h V_h^{\text{hist}} = w_h (C V_h)$$


同样应用结合律：

$$\text{out}_h = (w_h C) V_h = c_{\text{sum}} V_h$$


* 权重行向量 $w_h$（形状 $1 \times S$）首先与显存中的历史矩阵 $C$（形状 $S \times 512$）相乘，将长达 $S$ 步的全部历史信息直接折叠为单根长度为 512 的汇总向量 $c_{\text{sum}}$。
* 随后，$c_{\text{sum}}$（形状 $1 \times 512$）仅需执行单次矩阵乘法乘上 $V_h$（形状 $512 \times 128$），即可还原出当前头最终的 128 维输出向量 $\text{out}_h$。

在此计算结构下，各个头依靠各自独立的 $U_h$ 与 $V_h$ 维持相互独立的投影空间，而显存中在整个 decode 周期内仅保存紧凑的低维矩阵 $C$，历史位置的显式键值矩阵从未被物化生成。

### 把缓存写入与各头读取拆开

把单个位置的缓存行向量记为 $c = x W_{\text{mid}}$，第 $h$ 个头的键为 $k_h = c U_h$。将全部 $H = 4$ 个头的键横向拼成总行向量 $K_{\text{all}} = \begin{bmatrix} k_0 & k_1 & k_2 & k_3 \end{bmatrix}$（总宽度 $4D$），对应的第二级矩阵横向拼成 $U_{\text{all}} = \begin{bmatrix} U_0 & U_1 & U_2 & U_3 \end{bmatrix}$：

$$K_{\text{all}} = c U_{\text{all}} = (x W_{\text{mid}}) U_{\text{all}}$$

以每头宽度 $D$ 为一个分块单位：$W_{\text{mid}}$ 中的每个分块 $W_i$ 形状为 $(E \times D)$，负责从 $x$ 算出一段长为 $D$ 的向量 $c_i = x W_i$；$U_{\text{all}}$ 中的每个分块形状为 $(D \times D)$，其中 `I` 代表单位矩阵，`.` 代表全零矩阵，`p` 至 `w` 代表各自独立的稠密权重矩阵。四种机制从输入 $x$ 到 4 个头的键 $K_{\text{all}}$ 的完整数据流如下：

```
          输入 x     W_mid (按列分块)     c (写入 cache)     U_all (c → 各头 k)            4 个头的键 K_all
                                                             h0  h1  h2  h3
MHA       (1×E)    [W0 W1 W2 W3]       [c0 c1 c2 c3]       ┌  I   .   .   . ┐       [   c0   |   c1   |   c2   |   c3   ]
r = 4D              (E × 4D)             (1 × 4D)          │  .   I   .   . │
                                                           │  .   .   I   . │
                                                           └  .   .   .   I ┘

GQA       (1×E)    [W0 W1      ]       [c0 c1      ]       ┌  I   I   .   . ┐       [   c0   |   c0   |   c1   |   c1   ]
r = 2D              (E × 2D)             (1 × 2D)          └  .   .   I   I ┘

MQA       (1×E)    [W0         ]       [c0         ]       [  I   I   I   I ]       [   c0   |   c0   |   c0   |   c0   ]
r = D               (E × D)              (1 × D)

MLA       (1×E)    [W0 W1      ]       [c0 c1      ]       ┌  p   q   r   s ┐       [c0p+c1t |c0q+c1u |c0r+c1v |c0s+c1w ]
r = 2D              (E × 2D)             (1 × 2D)          └  t   u   v   w ┘
```

在这张图里，**$W_{\text{mid}}$ 的列块数决定了缓存向量 $c$ 的宽度，也决定了 $U_{\text{all}}$ 的高度（行数）**；而 **$U_{\text{all}}$ 的每一列（`h0` 至 `h3`）决定了对应头如何从 $c$ 中组合出自己的键**：

- **MHA（存 $4D$，秩 $r = 4D$）**：$W_{\text{mid}}$ 有 4 个独立列块，算出 4 段数据 $c = \begin{bmatrix} c_0 & c_1 & c_2 & c_3 \end{bmatrix}$ 存入显存。$U_{\text{all}}$ 的第 $h$ 列只在第 $h$ 行放一个单位阵 `I`，其余为 `.`，表示第 $h$ 个头原样切出第 $h$ 段数据。4 个头的键彼此独立。

- **GQA, $G = 2$（存 $2D$，秩 $r = 2D$）**：$W_{\text{mid}}$ 直接砍掉后两列，只算 2 段数据 $c = \begin{bmatrix} c_0 & c_1 \end{bmatrix}$ 存入显存。$U_{\text{all}}$ 的 `h0` 列与 `h1` 列完全相同（第一行均为 `I`），第 0 头和第 1 头切出同一段 $c_0$，导致 $k_0 = k_1 = c_0$。显存减半，代价是同组的头只能共用完全相同的键。

- **MQA（存 $D$，秩 $r = D$）**：$W_{\text{mid}}$ 只剩 1 个列块，显存只存 1 段 $c = \begin{bmatrix} c_0 \end{bmatrix}$。$U_{\text{all}}$ 的 4 列全部为 `I`，4 个头的键全部相等（$k_0 = k_1 = k_2 = k_3 = c_0$）。

- **MLA, $d_c = 2D$（存 $2D$，秩 $r = 2D$）**：前半程与 $G = 2$ 的 GQA 完全相同——$W_{\text{mid}}$（即 $W_{\text{down}}$）只算 2 段公共压缩数据 $c = \begin{bmatrix} c_0 & c_1 \end{bmatrix}$ 存入显存，总投影矩阵的秩同样被卡在 $r = 2D$。差别在后半程：$U_{\text{all}}$ 的 4 列不再是重复的 `I` 和 `.`，而是各头独立训练的稠密权重块：

    $$k_0 = c_0 p + c_1 t, \qquad k_1 = c_0 q + c_1 u$$

    由于 $(p, t)$ 与 $(q, u)$ 是两组不同的稠密权重，从同一份缓存 $\begin{bmatrix} c_0 & c_1 \end{bmatrix}$ 线性组合出的 $k_0$ 与 $k_1$ 互不相同（$k_0 \neq k_1$）。

此外，值（Value）的一侧不需要另外计算和缓存新的压缩向量，而是直接复用显存里的同一份 $c = \begin{bmatrix} c_0 & c_1 \end{bmatrix}$，只需将图中的 $U_{\text{all}}$ 替换为另一套独立训练的稠密权重矩阵 $V_{\text{all}}$，即可同样组合出 4 个头各自不同的值向量 $v_0, v_1, v_2, v_3$。

### 为什么不能直接在压缩键上做矩阵吸收：RoPE 的阻碍

把 $q_h (C U_h)^\top$ 改写成 $(q_h U_h^\top) C^\top$，前提是：**从缓存里的 $c_j$ 到最终打分之间，只能经过不随历史位置 $j$ 变化的固定线性映射。**

标准 Transformer 使用的旋转位置编码（RoPE）打破了这个前提。

在行向量体系下，第 $j$ 个历史位置的压缩向量 $c_j$（形状 $1 \times 512$）经 $U_h$（形状 $512 \times 128$）还原出键后，RoPE 会让它右乘一个随位置 $j$ 变化的旋转矩阵 $R(j)$（形状 $128 \times 128$）：

$$k_{j,h} = c_j U_h R(j)$$

当前位置 $t$ 的查询 $q_h$（形状 $1 \times 128$）同样右乘 $R(t)$。两者做内积打分时：

$$\text{score}_{t,j,h} = (q_h R(t)) (c_j U_h R(j))^\top = q_h R(t) R(j)^\top U_h^\top c_j^\top = q_h R(t - j) U_h^\top c_j^\top$$

问题就出在中间的相对位置旋转矩阵 $R(t - j)$ 上：

1. $R(t - j)$ 的数值取决于历史位置编号 $j$，每一个历史位置 $j$ 对应的矩阵都不同。
2. 矩阵乘法不满足交换律：$R(t - j) U_h^\top \neq U_h^\top R(t - j)$。

因为不能交换顺序，$U_h^\top$ 被依赖历史位置 $j$ 的 $R(t - j)$ 死死挡在右边，无法提前越过它与当前查询 $q_h$ 相乘。只要对压缩后的键直接施加 RoPE，矩阵吸收就无法成立，每一步 decode 依然要为全部 $S$ 个历史位置逐一还原并旋转。

同一机理也解释了为什么 Qwen3-0.6B 不能通过只缓存输入向量 $x$（宽 1024）来代替缓存 8 组键值（宽 2048）：其注意力层在乘完 $W_k$ 之后，紧接着要做 `k_norm`（RMSNorm 归一化，属于非线性缩放）和 RoPE 旋转。非线性算子与依赖位置的旋转矩阵共同封死了运算重排的可能，历史位置的计算无法转移到当前单 token 的查询一侧。

### Prefill 与 Decode 的计算取舍

矩阵吸收并不是没有代价的。重排之后，虽然省去了还原 $(S \times 128)$ 历史键值矩阵的开销，但每个头做注意力打分和加权求和时，内积的向量宽度从原本的 $D = 128$ 变成了 $d_c = 512$，单次内积的乘加运算量增加到了原来的 4 倍。

- **在 Decode 阶段**：每步只处理 1 个新 token，速度卡在显存读取带宽（Memory-bound）。用增加 4 倍片上乘加运算的代价，换取显存读取量的大幅降低，整体耗时明显缩短。
- **在 Prefill 阶段**：一次性并行处理整段提示词，速度卡在芯片浮点算力（Compute-bound）。此时若再把内积宽度撑大 4 倍，计算会明显变慢。因此推理引擎在 Prefill 阶段不使用矩阵吸收，而是按原顺序先将 $c$ 还原为 128 维的键与值，再执行标准的多头注意力计算。

### 解耦 RoPE

把“解耦 RoPE”拆开，其实就是在做一件非常简单的事：**既然一个向量同时要“省显存（做矩阵吸收）”又要“带位置信息（加 RoPE）”是做不到的，那就干脆备两个向量，一个专门负责省显存，另一个专门负责带位置信息，最后把它们拼在一起打分。**

之所以在代码和数学上完全等价，靠的是向量点积的一条基本性质：**两个拼接向量的点积，等于它们各自先做点积再把结果加起来。**

#### 第一步：温习向量拼接的点积性质

假设你的查询向量由两截拼成：左边 128 个数叫 $q_{\text{内容}}$，右边 64 个数叫 $q_{\text{位置}}$，总长 $128 + 64 = 192$。 对应的键向量也由两截拼成：左边 128 个数叫 $k_{\text{内容}}$，右边 64 个数叫 $k_{\text{位置}}$，总长也是 192。

```
完整的查询 Q_h (宽 192) = [   q_内容 (128 个数)   |  q_位置 (64 个数)  ]
                                    ×                     ×
完整的键   K_h (宽 192) = [   k_内容 (128 个数)   |  k_位置 (64 个数)  ]
```

当拿长 192 的 $Q_h$ 和长 192 的 $K_h$ 做内积（对应位置相乘再全部加起来）时，前 128 个数乘前 128 个数，后 64 个数乘后 64 个数，两边互不干扰：

$$\text{总内积} = (q_{\text{内容}} k_{\text{内容}}^\top) + (q_{\text{位置}} k_{\text{位置}}^\top)$$

看明白这个加法拆分，解耦 RoPE 的数据流就一目了然了——它就是把左半截（128 维）和右半截（64 维）分成两条完全独立的流水线去处理。

#### 第二步：两条流水线各自怎么走？

以 DeepSeek-V2（共 $H = 128$ 个头，输入 $x_j$ 宽 $5120$）在第 $j$ 个历史位置写入、第 $t$ 个当前位置读取为例：

```
历史位置 j 的输入 x_j (1 × 5120)
  │
  ├──► 【左路：内容通路 (负责省显存，不加 RoPE)】
  │       x_j × W_down (5120×512) ──► 算出 c_j (1×512)，直接存入显存 Cache
  │                                   (因为没加 RoPE，Decode 时靠矩阵吸收：q_h 先乘 U_h^T 变成 512 维，再和 c_j 点积)
  │
  └──► 【右路：位置通路 (负责记位置，加 RoPE，不压缩，全头共用)】
          x_j × W_kr   (5120×64)  ──► 算出 64 个数 ──► 乘旋转矩阵 R(j) ──► 得到 k_pe,j (1×64)，存入显存 Cache
                                   (128 个头共用这一份 64 维向量，其实就是 MQA)
```

把这两条路拆开細看：

##### 1. 左路：内容通路（128 维，走 MLA 矩阵吸收）

- **写入 Cache 时**：输入 $x_j$ 乘以 $W_{\text{down}}$，变成 512 个数的压缩向量 $c_j$ 存进显存。

- **为什么能吸收**：这一路**绝对不乘旋转矩阵 $R(j)$**。所以在 decode 打分时，第 $h$ 个头的解压矩阵 $U_h^\top$ 前面没有任何挡路的东西，可以直接乘到当前步的内容查询 $q_h$（128 维）上，算出 $\tilde{q}_h = q_h U_h^\top$（512 维）。

- **打分第一项**：直接拿 512 维的 $\tilde{q}_h$ 与显存里 512 维的 $c_j$ 做点积：

    $$\text{内容分} = (q_h U_h^\top) c_j^\top$$

##### 2. 右路：位置通路（64 维，走 MQA 全头共享）

- **为什么不能走左路**：如果只有左路，注意力打分里完全没有位置信息，模型分不清哪个字在前、哪个字在后。所以必须补上一截带 RoPE 的向量。

- **写入 Cache 时**：既然加了 RoPE 就没法做“解压矩阵吸收”，那这一截干脆**不做低秩压缩、也不用解压矩阵**。直接从输入 $x_j$（5120 维）乘一个小矩阵 $W_{kr}$（形状 $5120 \times 64$），算出 64 个数，然后直接乘上位置 $j$ 的旋转矩阵 $R(j)$，得到位置键 $k_{\text{pe}, j}$（形状 $1 \times 64$），原样存进显存。

- **怎么省显存**：如果 128 个头每个头都存一份 64 维的位置键，显存又要多出 $128 \times 64 = 8192$ 个数。为了省显存，这一路直接采用 **MQA 策略**——**所有 128 个头共用这同一份 64 维的 $k_{\text{pe}, j}$**。

- **查询侧怎么配合**：在当前位置 $t$，每个头 $h$ 各自有一个 64 维的位置查询 $q_{\text{pe}, h}$（各头不同），乘上当前位置 $t$ 的旋转矩阵 $R(t)$。

- **打分第二项**：直接拿当前头旋转后的 $q_{\text{pe}, h}$（64 维）去和显存里那份共用的 $k_{\text{pe}, j}$（64 维）做点积：

    $$\text{位置分} = q_{\text{pe}, h} k_{\text{pe}, j}^\top$$

#### 第三步：汇总显存与最终打分

**显存里每个位置到底存了什么？** 把左路和右路存进显存的东西拼在一起，每层、每个 token 位置只需要存两样东西：

```
单位置 KV Cache (共 576 个数) = [   左路：公共压缩向量 c_j (512 个数)   |   右路：公共位置键 k_pe,j (64 个数)   ]
```

- 左边的 512 个数同时管 128 个头的**内容键**和**值（Value）**。
- 右边的 64 个数专门管 128 个头的**相对位置（RoPE）**。
- 两者加起来，一个位置只占 $512 + 64 = 576$ 个数。

**2. 最终注意力分数怎么算？** 把左路算出的“内容分”和右路算出的“位置分”加起来，再除以总宽度（$128 + 64 = 192$）的平方根做缩放：

$$\text{score}_{t, j, h} = \frac{\overbrace{(q_h U_h^\top) c_j^\top}^{\text{左路：512 维点积（矩阵吸收，无位置）}} + \overbrace{q_{\text{pe}, h} k_{\text{pe}, j}^\top}^{\text{右路：64 维点积（带 RoPE，MQA 共享）}}}{\sqrt{128 + 64}}$$

这就是“解耦 RoPE”的全部内容：**把“内容”和“位置”拆成两截；占大头的内容部分（128 维）不加 RoPE，用 MLA 的矩阵吸收省显存；占小头的位置部分（64 维）加 RoPE，用 MQA 的全头共享省显存。**

## 吸收的代价与两条执行路径

吸收省掉了逐个历史位置的还原，但打分与加权的宽度从每头 $D = 128$ 变成了压缩向量宽度 $d_c = 512$。显式还原与矩阵吸收两种做法的运算量随本轮新位置数 $L$ 的变化方式完全不同：

* **显式还原**：先把全部 $S$ 个历史位置的 $c$（宽 $d_c = 512$）还原成每个头的 $k_h$、$v_h$（宽 $D = 128$），这笔开销与历史长度 $S$ 成正比，但与新位置数 $L$ 无关；随后每一对（新位置，历史位置）都在较窄的 $D = 128$ 维上打分和加权。
* **矩阵吸收**：先对 $L$ 个新位置的查询乘 $U_h^\top$、最后对 $L$ 个新位置的输出乘 $V_h$，这笔开销只与 $L$ 成正比；但随后每一对（新位置，历史位置）都必须在较宽的 $d_c = 512$ 维上打分和加权。

`mlx_lm` 0.31.3 的 DeepSeek-V3 实现（`mlx_lm/models/deepseek_v3.py`）正是按上面的分界拆成两条执行路径。代码中的字段与前文记号一一对应：输入 $x$ 先投影并切成 $c$（宽 $d_c = 512$）与 $k_{\text{pe}}$（宽 $d_r = 64$），$c$ 再过一次 RMSNorm（`kv_a_layernorm`），然后只把 $c$ 与旋转后的 $k_{\text{pe}}$ 写进 cache——因为 `kv_a_layernorm` 发生在写进 cache 之前，从缓存里的 $c$ 到打分之间依然只有线性映射，不影响后续的矩阵吸收。计算注意力时，先算出位置部分的打分 `pe_scores`，再以 `L == 1` 为界分岔：

```text
decode (L = 1)
  q_nope (每头 D=128) ── embed_q (U_h^T) ──> 每头 d_c=512 ──┐
  c (d_c=512, 从 cache 读) ─────────────────────────────────┼─> 在 512 维上打分与加权 ──> unembed_out (V_h) ──> 每头 D=128 ──> o_proj
  pe_scores (q_pe · k_pe, 宽 d_r=64 的位置打分) ─────────────┘
  每个头的 k_h、v_h 始终没有出现

prefill (L > 1)
  c (d_c=512) ── embed_q (U_h) ──────> 每头 k_h (D=128) ──┐
  c (d_c=512) ── unembed_out (V_h) ──> 每头 v_h (D=128) ──┼─> 在 128 维上打分与加权 ──> o_proj
  pe_scores ──────────────────────────────────────────────┘
```

同一个包里的 DeepSeek-V2 旧实现（`mlx_lm/models/deepseek_v2.py`）则是反面例子：它在写入 cache 之前，先把 $c$ 显式还原成全部 128 个头的 $k_h$、$v_h$，再把位置键 $k_{\text{pe}}$ 复制 128 份拼在每个头的 $k_h$ 后面，最后把拼好的大张量写进 cache。结果每个位置每层存了 $128 \times (128 + 64 + 128) = 40,960$ 个数，比标准 MHA 的 $32,768$ 个数还多 25%。MLA 架构提供了每个位置每层只存 576 个数的数学结构，真正省下显存必须靠实现层缓存 $c$ 与 $k_{\text{pe}}$ 并在 decode 时执行矩阵吸收——同一模型架构的两种代码实现，cache 占用相差约 71 倍（$40960 / 576 \approx 71.1$）。

把视角拉远，本篇讨论的四种形态都在回答「cache 的大小能否不随查询头数 $H$ 增长」，MLA 用共享低维子空间给出了兼顾容量与多头独立性的答案。回到开篇的读取量公式 `2 × G × D × b × N × S`，另外两个因子也在回答平行的问题：一个是历史长度 $S$——滑动窗口让每层只保留最近若干个位置，线性注意力层把逐位置追加的 cache 换成固定大小的状态矩阵，两者都让 cache 不随 $S$ 无限增长（其中线性注意力在思路上与 MLA 平行，都是改变存放物，只是压缩的维度从头数 $H$ 换成了序列长度 $S$）；另一个是每个数的字节数 $b$——KV 量化不改变存放物，只减少每个数的比特数，但它与 MLA 结合时会产生新的问题：MLA 缓存的是压缩向量 $c$，量化 $c$ 产生的舍入误差会经过每个头的解压矩阵 $U_h$、$V_h$ 放大或扩散进打分与输出，这与在 MHA/GQA 中直接量化已经成型的 $k$、$v$ 具有不同的误差传播性质。
